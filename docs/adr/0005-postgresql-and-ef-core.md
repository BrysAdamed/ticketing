# 5. PostgreSQL with EF Core (Npgsql)

- Status: Accepted
- Date: 2026-10-26

## Context

The brief requires PostgreSQL. Everything runs on one VM with one database (D-03, D-04), including attachment content (D-15) and search (D-39). The spec fixes several storage rules: application-generated UUIDv7 ids, `xmin` as row version, per-project counters, rank collation and full text search ([spec §2](../product/01-refined-spec.md#2-cross-cutting-conventions), [§4.5](../product/01-refined-spec.md#45-ticket), [§6.6](../product/01-refined-spec.md#66-ranking), [§6.8](../product/01-refined-spec.md#68-search-lists-and-export)).

## Decision

- **PostgreSQL 18**, accessed through **EF Core 10** with `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3. `Microsoft.EntityFrameworkCore.Relational` and `.Design` are pinned to 10.0.14 through Central Package Management with transitive pinning (research R9).
- **Naming:** snake_case tables and columns (as used in the spec's SQL), applied by a model-building convention in Infrastructure. One `IEntityTypeConfiguration<T>` per entity.
- **Ids:** `Guid` UUIDv7 generated by the application (`Guid.CreateVersion7()`), so ids are time-ordered and index-friendly and known before insert.
- **Concurrency:** every mutable aggregate maps PostgreSQL's system column `xmin` as its row version (`uint`, `IsRowVersion()`). The API exposes it as `rowVersion`; `If-Match` or MCP `expectedVersion` sets the original value, and a stale value yields `409` with current state.
- **Time:** `timestamptz` mapped to `DateTimeOffset` with offset zero.
- **Labels:** `text[]` with a GIN index. "All of" filters translate to `@>`, hints to `SELECT DISTINCT unnest(labels)`.
- **Test case steps** (and their snapshots in regression items): `jsonb` array, mapped through a JSON conversion. The list is always read and written whole, and `jsonb` lets a step later become an object (for example action + expected) without changing the column type.
- **Search:** a stored generated `tsvector` column `setweight(to_tsvector('english', title), 'A') || setweight(to_tsvector('english', coalesce(description, '')), 'B')` with a GIN index, queried with `websearch_to_tsquery('english', ...)` and ranked with `ts_rank`. A `pg_trgm` GIN index on `title` covers partial words. An exact key match (`WEB-42`, `WEB-TC-7`) is tried first.
- **Counters:** `next_ticket_number`, `next_test_case_number` and `next_regression_number` are incremented with `UPDATE project SET ... = ... + 1 WHERE id = @id RETURNING ... - 1` inside the insert transaction. The row lock serializes creation per project. A unique index on `(project_id, number)` is the backstop. Numbers are never reused; the design does not promise the absence of gaps.
- **Rank:** `text` column with `COLLATE "C"` and indexes per container (see [ADR 0010](0010-fractional-index-ranking.md)).
- **Attachments:** content in `attachment_content` (`bytea`) behind `IAttachmentStore` (D-15).
- **Soft delete:** global query filters on `deleted_at IS NULL` for tickets, projects and boards. Admin and history queries opt out explicitly.
- Partial unique indexes enforce spec uniqueness that depends on state, for example project name among non-deleted projects and PAT name among a user's non-revoked tokens.

## Consequences

- One engine covers relational data, arrays, JSON, search and binary content. One `pg_dump` backs up everything ([ADR 0012](0012-deployment-docker-compose.md)).
- `xmin` changes on **any** row update. Two cases matter:
  - Comments, links and attachments bump the ticket's `UpdatedAt` (spec §4.5), so they also change its row version. A user editing a field while someone else comments gets a `409`. The UI must handle `409` by refreshing and, where the server change touched other fields, re-applying the user's change.
  - Counters live on the project row (spec §4.5), so creating a ticket changes the project's row version. The project settings form will see `409` after any ticket creation. If this proves annoying, the counters move to a `project_counter` table; that would be a spec change.
- The `english` text configuration stems words ("tests" matches "test") but can mangle identifiers. Exact key lookup and the trigram index cover codes and partial words.
- Raw SQL is needed in a few places (counters, generated column, rebalancing). Each is wrapped in one Infrastructure method with an integration test.

## Alternatives considered

- **SQL Server.** Not what the brief asked for; no `text[]`, weaker JSON and full text story.
- **Dapper only.** Faster raw reads, but we would hand-write change tracking, migrations and concurrency. EF projections are fast enough for the latency targets (spec §10); Dapper can be added for a hot query if profiling demands it.
- **Integer identity keys.** Leak counts and need a round trip before related rows can be built. Human-friendly numbers already exist where needed (keys).
- **A dedicated `row_version` column or `bytea` timestamp.** Requires triggers or application bookkeeping; `xmin` is free and maintained by PostgreSQL.
- **One PostgreSQL sequence per project.** Requires DDL at project creation and cannot roll back with the transaction.
- **`simple` text configuration** (suggested in the research). Better for identifiers, no stemming. The spec chose `english`.
- **Elasticsearch or similar.** One more container for no gain at D-04 scale (D-39).
