# Ticketing v1: refined specification

Source: [00-original-brief.md](00-original-brief.md). Open questions and the reasoning behind each choice live in [../decisions.md](../decisions.md) (IDs `D-xx`). Improvements and their triage are in [02-improvements-triage.md](02-improvements-triage.md) (IDs `I-xx`). Items deferred past v1 are in [../ideas.md](../ideas.md).

This document is normative. "Must" means a test should exist for it. Where this spec and the brief disagree, this spec wins; the decision log says why.

## 1. Scope of v1

In v1:

- Local user accounts managed by an Admin, global roles, personal access tokens (PATs).
- Projects (public or private) with members and project roles.
- Tickets with keys, hierarchy, links, comments, attachments, activity history.
- Project backlog, multi-project boards, ranking by drag and drop.
- Test cases per project, regression sessions with result recording and bug creation.
- Per-project dashboard.
- Search with structured filters, quick jump, CSV export.
- Feature flags with user, role and percentage targeting, and a view-variant mechanism ready for A/B tests.
- REST API (OpenAPI) and an MCP server over HTTP that exposes the same use cases.
- Admin audit trail.

Explicitly not in v1 (see [ideas.md](../ideas.md)): SSO/OIDC, email (in-app notifications followed v1 with TKT-5, section 6.16), sprints as a concept, custom fields, configurable workflows, real-time board updates, Jira importer, time tracking, i18n, mobile layout. Dark mode is in v1 because the design tokens make it nearly free (light default, dark via user toggle / OS preference).

Onboarding (section 14, epic TKT-52) followed v1: a welcome dialog, a getting-started checklist, guided tours, contextual hints, What's new highlights, a Help menu and MCP server instructions. LATER for onboarding (see [ideas.md](../ideas.md)): an admin-editable tour CMS (I-127), onboarding analytics and funnels (I-128; the ADR 0008 exposure hook is the seam), video content (I-129), i18n of guide copy (I-60; copy lives in data files with stable ids), a Docs tour, the full Preferences tab (I-130), email invites (I-31, I-70) and sample projects (I-131).

Deployment target: Docker Compose on an internal VM (API + Angular static files + PostgreSQL) (D-03).

## 2. Cross-cutting conventions

| Topic | Rule |
| --- | --- |
| Identifiers | Every entity has `Id: uuid` (UUIDv7, generated by the application). Tickets, test cases and regression sessions also have a human key (section 6.1). APIs accept either the id or the human key wherever a ticket, test case or session is referenced. |
| Time | All timestamps are `timestamptz`, stored and transferred in UTC (ISO 8601). The UI renders in the browser's time zone. Week-based statistics use ISO weeks (Monday start) in UTC. |
| Text | All strings are trimmed on input. Empty after trimming equals null for optional fields and is a validation error for required ones. Lengths are counted in UTF-16 code units (what .NET `string.Length` and JS `length` return). |
| Markdown | CommonMark + GitHub-flavoured tables, strikethrough, task lists and autolinks. Raw HTML is not rendered. Output is sanitized on the client. Ticket keys matching `\b[A-Z][A-Z0-9]{1,9}-\d+\b` render as links to the ticket (I-09). |
| Enum transport | Enums travel as their exact PascalCase names listed in section 3 (for example `ReadyForTesting`). Display labels are a UI concern. |
| Concurrency | Every mutable aggregate has a `RowVersion` (PostgreSQL `xmin`). Updates accept an optional expected version (HTTP `If-Match`, MCP `expectedVersion`). If supplied and stale, the server returns 409 `concurrency.conflict` and the client refetches. The field is exposed as `rowVersion` (Ticket already has a business `Version`). The web UI sends it only for title/description saves (D-43). Updates are PATCH-style: omitted fields stay unchanged. |
| Pagination | Cursor-based. `limit` defaults to 25, maximum 100. Responses carry `nextCursor` (null on the last page). |
| Deletion | Users, projects and tickets are never hard-deleted in v1. Section 6 states the rule per entity. |
| Errors | RFC 9457 problem details with a stable machine `code` (for example `ticket.parent.cycle`), a human `title`, and per-field `errors`. MCP returns the same code and message (section 11). |
| Source tracking | Every write records its channel: `Web`, `Api` (PAT over REST) or `Mcp` (PAT over MCP). Activity history shows it (I-02). |

## 4. Domain model

Types: `uuid`, `text(n)` = string of at most n characters, `md(n)` = markdown string of at most n characters, `int`, `bool`, `timestamptz`, `T[]` = ordered list. `?` marks optional (nullable). "Unique" means enforced by a database constraint.

| --- | --- | --- |

| SetPasswordTokenHash | text? | SHA-256 of a one-time token. |
| SetPasswordTokenExpiresAt | timestamptz? | |
| CreatedAt, CreatedById | timestamptz, uuid? | CreatedById null for the bootstrap admin. |
| LastLoginAt | timestamptz? | |
| DeactivatedAt, DeactivatedById | timestamptz?, uuid? | |
| AvatarIcon | text(32)? | A key of the code-defined avatar catalogue (`AvatarCatalog`, animal icons), else `user.avatar.unknown`. Null shows initials. Keys that later leave the catalogue are treated as null (D-129). |
| AvatarColor | text(32)? | A named palette colour (`blue`, `violet`, `pink`, `orange`, `amber`, `green`, `teal`, `cyan`), else `user.avatar.color.unknown`. Null uses the colour hashed from the user id (D-129). |

Invariants:

- At least one active `Admin` exists at all times. Demoting or deactivating the last active Admin fails with `user.lastAdmin`.
- A user cannot change their own `GlobalRole` or deactivate themselves.
- Failed sign-ins are counted per account and client address (`LoginThrottle`: UserId, ClientAddress, FailedCount reset on success, LockedUntil, LastFailedAt; D-74). Web sessions are stored server-side (`UserSession`: Id, UserId, CreatedAt, LastSeenAt; D-75).
- Users are never deleted (D-12). Deactivation blocks login, rejects all PATs (they are revoked), and removes the user from pickers. Existing references (assignee, reporter, comments, history) stay and render as "Name (deactivated)".
- A deactivated user cannot become a new assignee or project member. Reactivation restores login. Revoked PATs stay revoked.
- Deactivating a user who is the last `Owner` of any non-archived project fails with `user.lastProjectOwner` and lists the projects. The Admin first adds another owner (Admins can manage any project).

| Field | Type | Constraints |

## 5. Permissions

### 5.1 Effective project access

A user's effective access to a project is computed in this order:

1. Inactive user: none.
2. Admin: `Owner` on every project, public or private.
3. Explicit membership: the membership role.
4. Public project, no membership: `Member` (D-02). Any signed-in user can write to a public project.
5. Private project, no membership: none. The API returns 404, never 403, so private projects do not reveal they exist.

On a public project, a `Viewer` membership has no effect beyond rule 4: the user still gets `Member` access. The UI hides the Viewer option for public projects and shows existing Viewer rows as "Member (public project)". Switching a project from public to private makes Viewer memberships meaningful again.

| Add, remove members; change member roles | Yes | No | No | No |
| Archive or unarchive the project | Yes | No | No | No |
| Delete the project | Admin only | No | No | No |

On an archived project every write action above is denied for everyone, except unarchive and watching, which only changes the caller's own state.

Ticket deletion and moderating other people's comments stay with Owners even on public projects. The product owner's rule opens "create/edit" to everyone; deletion is destructive and not editing (D-02).

### 5.4 Board actions

| Action | Board owner | Admin | Any other signed-in user |
| --- | --- | --- | --- |
| See the board and its name, description and linked project names it can read | Yes | Yes | Yes |
| See a card | Only if the viewer can read the ticket's project | same | same |
| Rename, edit description, transfer ownership, archive, unarchive, delete | Yes | Yes | No |
| Link a project | Yes, if the board owner can write to that project | Yes | No |
| Unlink a project | Yes | Yes | No |
| Place, move, rank a ticket on the board, or send it back to the backlog | Needs write access to the ticket's project | same | same |

Boards are visible to every signed-in user (D-07). Cards from projects the viewer cannot read are omitted entirely: not counted, not hinted at. Column counts and WIP numbers are computed per viewer. Linked private projects the viewer cannot read are omitted from the board's project list.

### 5.5 PAT scope

A PAT acts as its user, with the user's current permissions, intersected with its scope. `ReadOnly` tokens can only call read endpoints and read MCP tools. No PAT can manage PATs, change passwords or manage users and flags. Those endpoints accept only the cookie session.

## 6. Business rules and workflows

### 6.1 Keys

- Ticket: `{ProjectKey}-{n}`. Test case: `{ProjectKey}-TC-{n}`. Regression session: `{ProjectKey}-R-{n}`. Each has its own per-project counter starting at 1.
- Numbers are never reused. Soft-deleted tickets keep their numbers.
- The project key is immutable, so keys stay stable in commit messages, chats and LLM context.

### 6.2 Ticket lifecycle

- Create: requires Title and Type. Everything else defaults (Status `ToDo`, Priority `Medium`, in backlog at the bottom unless a board and position are given).
- Edit: any field except Id, ProjectId, Number, CreatedAt/By. Each changed field writes an ActivityEntry.
- Status transitions are free: any status may move to any other (D-05). Side effects:
  - Entering `Done`: `ResolvedAt = now`, `Resolution` = given value or `Done`.
  - Leaving `Done`: `ResolvedAt = null`, `Resolution = null`.
  - Any change: `StatusChangedAt = now`.
  - If the ticket sits on an archived board and leaves `Done`, it moves to the top of its project backlog.
- Delete (Owner only): soft delete. Fails with `ticket.hasChildren` if the ticket has non-deleted children; the user must reparent or delete them first. On delete: `BoardId = null`, links are removed, test cases pointing to it get `TicketId = null`, regression items keep `BugTicketId` but render it as "deleted". Deleted tickets disappear from every list, search and board. Opening a deleted ticket's key shows "WEB-42 was deleted by X on date". An Owner can undo a delete within 10 minutes (`POST /tickets/{key}/restore`, D-82); a general restore of older deletions is LATER.

### 6.3 Parent and child

- Parent and child must be in the same project (D-06).
- `Epic` cannot have a parent.
- Any non-Epic type may have a parent of any type.
- Maximum depth is 3 levels (for example Epic > UserStory > Technical). Setting a parent that would create a 4th level fails with `ticket.parent.depth`.
- Cycles are rejected with `ticket.parent.cycle` (the depth rule already prevents most, the server checks explicitly).
- Changing a ticket's type to `Epic` fails if it has a parent. Changing it from `Epic` is allowed if the depth rule still holds for its subtree.
- Children are independent of the parent's status, board and backlog placement. No automatic status roll-up. A move may bring the sub-tickets that are still in the place the parent is leaving and not Done along, on request (D-107).
- The ticket view lists direct children with status and a progress bar by status category.

### 6.4 Backlog and boards

- A ticket is in exactly one container: its project backlog (`BoardId = null`) or one board (`BoardId` set). Never both.
- The backlog view lists the project's tickets with `BoardId = null`, ordered by Rank. Done tickets are hidden unless "Show done" is on.
- A board shows one column per `TicketStatus`, in enum order. All 8 columns are always present and the board scrolls horizontally. Cards inside a column are ordered by Rank.
- Placing a ticket on a board requires that the board links the ticket's project and is not archived, and that the actor can write to the project.
- Moves: backlog to board, board to backlog, board to another board. Each is one operation and one ActivityEntry (`ticket.moved`). Status does not change on a move unless the move targets a specific column.
- Default positions: new ticket in the backlog goes to the bottom. A ticket sent back to the backlog goes to the top. A ticket placed on a board without a position goes to the bottom of its status column.
- Multi-select in the backlog and on boards, then drag or "Move to..." moves several tickets in one operation (I-11).
- Unlinking a project from a board returns that project's tickets on the board to the backlog top, keeping their relative order. The UI confirms with the count.
- Board archive (I-11): the owner chooses where non-Done tickets go: their project backlogs (top) or another non-archived board that links their projects. Tickets whose project the target board does not link go to the backlog. Done tickets stay on the archived board as a record of what was finished there. Archived boards are read-only and listed under "Archived boards". Unarchive is allowed.
- Board delete: all its tickets, including Done ones, go to their backlogs (top). The board is soft-deleted.

This covers the sprint-like flow most Jira teams use: pull tickets from backlogs onto a board, work them, archive the board and carry over unfinished work (D-09).

### 6.5 Private projects on shared boards

Rules in 5.4. Additionally:

- Search, MCP and REST board endpoints apply the same filter. A board fetched by a user returns only cards they can read.
- If a project becomes private, its tickets stay on boards and disappear for users who lose access.

### 6.6 Ranking

- `Rank` is a fractional-index string (base-62 digits, the algorithm used by the `fractional-indexing` family of libraries), compared with `COLLATE "C"`.
- Ordering scope is the container: one project's backlog, or one board. On a board, a column's order is the board order filtered by status.
- Moving a ticket between neighbours A and B sets `Rank = between(A.Rank, B.Rank)`. Moving into an empty container or column uses the container's last rank (or none) as the lower bound.
- If a generated rank exceeds 64 characters, the server rebalances the whole container in the same transaction (evenly spaced short keys, order preserved).
- Rank is never shown to users.

### 6.7 Field hints (version, labels)

- `GET hints` returns distinct values used in the project's non-deleted tickets (versions also include regression session versions), filtered by case-insensitive prefix, ordered by most recent use, at most 20.
- Hints are suggestions. Any valid new value is accepted.
- Labels are stored lower-cased, so "Backend" and "backend" are the same label.

### 6.8 Search, lists and export

- Quick jump (Ctrl+K or `/`): typing a ticket, test case or doc key opens it directly. Otherwise it searches ticket titles across readable projects and shows the top 10, then the top 5 docs (12.7) (I-03, I-04).
- Ticket search filters: projects, text, type, status, status category, priority, severity, assignee (including "unassigned" and "me"), reporter, labels (all of), version, parent, location (backlog, any board, a given board), created and updated date ranges, watching (tickets I watch, 6.15), include deleted = no. Sort: updated, created, priority, key, rank.
- Text search uses PostgreSQL full text (`websearch_to_tsquery('english', ...)`) over title (weight A) and description (weight B), plus a trigram index on title for partial words. Comments are not searched in v1.
- Every filter state is in the URL, so searches can be bookmarked and shared (I-21).
- CSV export of the current search result, at most 10 000 rows, all scalar fields plus labels joined by `;` (I-12).
- "My work" page: open tickets assigned to me across all projects, grouped by project, and my assigned waiting regression items (I-08); plus "Watching": open tickets I watch but am not assigned to, most recently updated first, at most 100 (the full list is the `watching=true` search).

### 6.9 Comments

- Markdown, 1..20000 characters.
- The author can edit and delete their own comments at any time while they have write access. Edits set `EditedAt`; the previous body goes to ActivityEntry, so history keeps it.
- Project Owners can delete any comment on the project.
- Deleting clears the body and keeps a "Comment deleted" placeholder in order.
- Mentions (I-33, D-96), in comments and ticket descriptions only: stored as `@[Display Name](user:<id>)`; clients may also write `@email`, which the server stores in that form when the address belongs to an active user who can read the project (an unknown address stays text). Mentions inside code spans, fenced code blocks and indented code blocks outside lists do not count (D-159). A newly added mention (compared with the previous text) of a user who is inactive, unknown or cannot read the project fails with 400 `mention.invalid` (field `description` or `body`, with a hint); mentions already in the previous text are never re-checked. Each newly mentioned user other than the author starts watching (6.15) and is notified (6.16); edits that add no mention notify nobody. Tickets and comments return `mentions`: the mentioned users who are active and can read the project now; clients render other mentions as plain text. The web editors for descriptions and comments offer a people picker on `@` (`GET /users?projectKey=KEY&access=read`).

### 6.10 Test case lifecycle

- Created from the project's test case view or from a ticket (which pre-fills `TicketId`). The ticket view lists its test cases.
- Status: `New` on creation. Any status may change to any other, with the rule that `Manual` needs at least one step. `New` means "not ready" and is excluded from regressions.
- Edits never change running or completed regression sessions (they hold snapshots).
- Archive hides the case from default lists and from future sessions. Unarchive restores it.
- Hard delete is allowed only if the case never appeared in a session. Otherwise only archive.
- The test case list shows counts by status and filters by status, linked ticket and text.

### 6.11 Regression session lifecycle

Start (any user with write access):

1. Requires at least one non-archived test case with status `Manual` or `Automatic`. Otherwise fails with `regression.noEligibleCases`.
2. In one transaction: allocate the session number, create the session (`InProgress`), and create one item per eligible test case with a snapshot of its fields.
3. `Manual` cases become items with `WaitingForExecution`. `Automatic` cases become items with `Passed`, `ExecutedById = null`, `ExecutedAt = StartedAt`, and the UI labels them "auto-passed" (D-13).

Several sessions may run in parallel in one project, for example for two versions.

Execution (while the session is `InProgress`):

- "Take": any user with write access assigns an item to themselves, including taking it over from another assignee. The UI asks for confirmation when taking over.
- Owners can assign an item to any user with write access, or unassign it.
- Only the current assignee records a result. Recording a result on an unassigned item assigns it to the actor first.
- Results: `Passed`, `Failed`, `Skipped`, or back to `WaitingForExecution`. Any result can change to any other while the session is in progress. Each change writes an ActivityEntry for the session.
- `Failed` requires `ResultNote` (actual result).
- When an item becomes `Failed`, the UI opens the "Create bug" dialog pre-filled (the user can cancel). MCP and REST take an optional `createBug` flag on the same call.

Bug creation from a failed item:

- Allowed once per item. If `BugTicketId` is set, the UI shows the link instead.
- Ticket fields: project = session project; Type `Bug`; in the backlog at the top; Title `[Regression] {test case title}` truncated to 255; Severity `Major`; Priority `High`; Version = session version; Labels = `regression`; Reporter = actor; Assignee empty. All editable in the dialog before saving.
- Description template:

  ```markdown
  Found in regression session WEB-R-3 "Regression 2026-11-02" (version 1.4.0) by Jane Doe on 2026-11-02.
  Test case: WEB-TC-7 "Log in with valid credentials"

  ## Preconditions
  {snapshot preconditions, or "None"}

  ## Steps to reproduce
  1. {step 1}
  2. {step 2}

  ## Expected result
  {snapshot expected result, or "Not specified"}

  ## Actual result
  {item ResultNote}
  ```

- The item stores `BugTicketId`. If the test case has a non-deleted `TicketId`, a `RelatesTo` link is created between the bug and that ticket.

Completion and cancellation:

- Complete: allowed when no item is `WaitingForExecution`. "Skip remaining" (any user with write access, same as complete) sets all waiting items to `Skipped` with note "Skipped at completion". After completion the session and items are immutable.
- Cancel: Owner or session starter, while `InProgress`. Cancelled sessions are read-only and excluded from dashboard trends.
- Session summary (shown in list and detail): total, passed (manual and auto split), failed, skipped, waiting, pass rate = passed / (passed + failed), bugs created.

### 6.12 PAT lifecycle

- Create: name, scope, expiry. The full token is shown once, with a copy button and a ready-to-paste Claude Code MCP config snippet. Only the hash is stored.
- List: name, prefix, scope, created, expires, last used, status (active, expired, revoked). Tokens expiring within 7 days get a warning badge.
- Revoke: immediate. Revoked and expired tokens stay listed for 90 days, then are purged.
- Authentication: `Authorization: Bearer tkt_...` on REST and MCP. Failures return 401 without saying whether the token exists.
- Limits: 20 active tokens per user. Rate limit 600 requests per minute per token (429 with `Retry-After`).
- Deactivating a user revokes all their tokens.

### 6.13 Feature flags and view variants

Evaluation for a signed-in user, first match wins:

1. Flag does not exist: `off`.
2. `Enabled = false`: `off`.
3. User id is in `TargetUserIds`: `on`.
4. User's global role is in `TargetRoles`: `on`.
5. `bucket(flagKey, userId) < RolloutPercentage`: `on`. `bucket` = first 4 bytes of SHA-256(UTF-8 `"{flagKey}:{userId}"`) as unsigned big-endian integer, mod 100. Stable across restarts and across C# and TypeScript.
6. Otherwise `off`.

Contract: `GET /api/v1/me/flags` returns `{ "flags": { "<key>": "<variant>" } }` where the variant is `on` or `off` in v1. The variant is a string, not a boolean, so multi-variant A/B tests can add variants later without changing clients. The Angular app loads flags once at startup and on window focus if older than 5 minutes.

View variants (A/B readiness, D-14): every routed page is resolved through a view registry keyed by a view id (for example `ticket-detail`). In v1 each view has exactly one variant, `default`. A view may name a flag; the registry renders the component registered for that flag's variant and falls back to `default`. No page imports another page's component directly. This is the only A/B work in v1; no second variants are built.

Flag changes write ActivityEntries. Admin UI: list, create, edit, delete; shows how many users currently evaluate `on` (computed from active users).

### 6.14 User and authentication lifecycle (D-01)

- Bootstrap: on startup, if no users exist, create an Admin from environment variables `TICKETING_BOOTSTRAP_ADMIN_EMAIL` and `TICKETING_BOOTSTRAP_ADMIN_PASSWORD`. Startup fails if they are missing and the user table is empty.
- Admin creates a user with email, display name and global role. The system returns a one-time set-password link valid 72 hours, which the Admin passes on. No email is sent in v1. The Admin never sees or sets the password.
- Forgotten password: an Admin issues a new set-password link (valid 24 hours). Issuing one invalidates the old password only when the link is used.
- Password policy: 12..128 characters, not equal to the email, checked against a bundled list of the 10 000 most common passwords. No composition rules.
- Lockout: 5 failed logins in a row from one client address lock the account for that address for 15 minutes; other addresses can still sign in (D-74). A locked account, an unknown email and a wrong password all get the same answer, `401 auth.invalidCredentials`, after the same password-hashing work, so sign-in reveals neither which accounts exist nor which are locked. Sign-in is also rate limited per client address (20 per minute). The client address is the TCP peer unless the request came through a trusted proxy (D-73). Setting a password through a link lifts the account's lockouts.
- Web session: HttpOnly, Secure, SameSite=Lax cookie with 12 hour sliding expiry, plus anti-forgery protection on cookie-authenticated writes. The session is also stored on the server; signing out deletes it, so a copied cookie stops working (D-75).
- Users change their own display name, avatar and password (current password required for the password). The avatar is one of 32 animal icons (or initials) on one of the 8 palette colours (or the automatic hashed colour), picked on Profile → General and saved at once (D-129, D-130). They can also turn achievements off there, which deletes their achievement data, and back on (15.11).
- Deactivate and reactivate per 4.1. No hard delete.

### 6.15 Watchers (I-32, D-93)

- Anyone who can read a ticket can watch or unwatch it: viewers too, and on archived projects too. Both are idempotent and need write-scoped credentials. The ticket view has a Watch/Unwatch toggle (shortcut `w`) with the watcher count and avatars.
- Automatic watching, applied in the same transaction as the write that triggers it, whatever the channel: the reporter and the assignee of a new ticket, each new assignee, anyone who comments, and anyone newly @mentioned (6.9, D-96). Users who cannot read the project or are deactivated are skipped. Unwatching holds until the next such trigger.
- Watcher lists show only active users who can currently read the project, by display name. A watcher who loses access or is deactivated is hidden (and will get no notifications) but is shown again if access returns. Watcher data is never visible for an unreadable ticket (404).
- REST: `GET /tickets/{key}/watchers`, `PUT /tickets/{key}/watchers/me`, `DELETE /tickets/{key}/watchers/me`, each returning `{ count, watching, users }`. The ticket (`GET /tickets/{key}`, `include=watchers`, part of the default) carries the same object as `watchers`.

### 6.16 In-app notifications (I-30, D-94)

- Triggers, created in the same transaction as the change whatever the channel (REST, MCP, bulk create, moves, board archive or delete, regressions):
  - Assigned: a ticket created with you as assignee, or reassigned to you.
  - RegressionItemAssigned: a regression item assigned to you by someone else (taking an item or recording a result assigns it to yourself and notifies nobody).
  - Mentioned: someone newly @mentions you in a ticket description or comment (6.9, D-96): "mentioned you in the description" / "mentioned you in a comment". On a ticket you watch, a new comment that mentions you notifies Mentioned instead of Commented.
  - On a page or diagram you created or commented on (comments that are not deleted): a new comment (Commented, "commented"), see 12.9.
  - On a ticket you watch (6.15): a new comment (Commented), a status change by PATCH or by moving to a board column (StatusChanged), a priority change to High or Highest from a lower priority (PriorityRaised; lowering or reaching Medium or below notifies nobody), a move between backlog and boards or between boards, including board archive carry-over and board deletion (Moved), and deletion (Deleted).
- The actor is never notified about their own action. Recipients must be active and able to read the project (5.1) at the time of the change; others get nothing.
- Collapsing: a change by the same actor on the same ticket (or regression session, or doc) within 5 minutes of the first change of an unread notification is merged into it: `eventCount` grows, `updatedAt` moves, and the headline (kind and summary) is replaced only by a higher-ranked kind (section 3). Several changes in one save collapse the same way. A read notification is never reopened; the next change starts a new one.
- Listing re-checks read access: notifications about projects the user can no longer read (removed membership, project made private, project deleted) are left out of the list and the unread count, and come back if access returns. Deleted tickets stay listed, flagged `deleted`.
- Mark read: some (1 to 100 ids) or all of the caller's notifications; ids of other users' notifications are ignored. Read time is kept on repeat. Needs write-scoped credentials.
- Retention: notifications older than 90 days are deleted by the hourly retention job.
- REST (`/api/v1/me/notifications`): `GET ?unread=true&cursor=&limit=` returns `{ items, nextCursor }`, newest first by `createdAt`; `GET /unread-count` returns `{ count }`; `POST /read` with `{ "ids": [...] }` or `{ "all": true }` returns `{ unreadCount }`. An item is `{ id, kind, summary, eventCount, actor, projectKey, ticket: { key, title, deleted } | null, regression: { sessionKey, sessionName, testCaseKey } | null, doc: { key, title, deleted } | null, url, createdAt, updatedAt, readAt }`; `url` is the SPA path of the ticket, the regression item or the doc's comments (`/p/{PK}/docs/{KEY}/{slug}#comments`).
- Performance: list (all or unread, first page) and unread count p95 under 50 ms with 100 000 notifications for one user.

## 9. MCP server

### 9.1 Transport and auth

- Streamable HTTP MCP endpoint at `/mcp`, hosted in the same API process. No local install. Claude Code connects with `claude mcp add --transport http ticketing https://<host>/mcp --header "Authorization: Bearer tkt_..."`.
- Every call runs as the PAT's user with that user's permissions and channel `Mcp`.
- `tools/list` returns only tools allowed by the token scope. Read tools carry `readOnlyHint: true`. `delete_ticket`, `delete_comment`, `unlink_tickets`, `cancel_regression_session`, `archive_board`, `delete_doc` and `delete_doc_comment` carry `destructiveHint: true` and `_meta["anthropic/requiresUserInteraction"]: true`, so Claude Code asks the user before every call even in a session that would otherwise run tools unasked (D-102). Every destructive tool carries both; an integration test on `tools/list` keeps the two sets equal.
- The `initialize` response carries server instructions: a short primer on Ticketing's model for the agent (14.8). The exact text is in [docs/mcp.md](../mcp.md#server-instructions).
- A client sends `Accept: application/json, text/event-stream` and the bearer token on every POST; the server is stateless, so no session id is kept between requests and `tools/call` works without a prior `initialize` on the same connection.
- `LastUsedAt` of the PAT is written on its first authenticated request and then at most every 5 minutes; the connection check (14.8) and the checklist read it.

### 9.2 Conventions for all tools

- Tickets, test cases and sessions are referenced by key (`WEB-42`, `WEB-TC-7`, `WEB-R-3`); ids are also accepted. Projects by key. Users by email or id. Boards by id.
- Enum inputs and outputs use the exact values in section 3. Each tool's description lists the allowed values so the model does not guess.
- Outputs are JSON objects with stable field names. Dates are ISO 8601 UTC. Markdown fields are returned raw.
- Lists return `{ items, nextCursor }`, `limit` default 25, max 100.
- Errors return `isError: true` with `{ code, message, hint }`. Example: `{ "code": "ticket.parent.depth", "message": "WEB-9 would be a 4th-level ticket", "hint": "Pick a parent whose own parent is an Epic or empty" }`.
- Write tools accept optional `expectedVersion`. Create tools accept optional `idempotencyKey`.
- A ticket summary is: key, title, type, status, priority, severity, assignee (email + name), storyPoints, labels, version, parentKey, location (`backlog` or board id + name), updatedAt, url.

### 9.3 Tools

Context and users

| Tool | Inputs | Output |

## 12. Docs

Each project has documentation: a tree of folders, markdown pages and diagrams (Mermaid or Canvas). The full feature spec, including the UI, links, search, history and PDF export, is [03-docs-refinement.md §1](03-docs-refinement.md#1-refined-v1-of-docs-spec); this section states the rules as built (epic TKT-10: TKT-12 to TKT-22, decisions D-108 to D-128).

### 12.1 Model and keys

- `DocNode` (one table for all kinds): `Kind` (`Folder`, `Page`, `Diagram`), `DiagramFormat` (`Mermaid`, `Canvas`; required for diagrams only), `ParentId` (null = project root, otherwise a folder of the same project), `Rank`, `Title`, `Content` (latest published copy; null for folders), `Outline` (Canvas labels for search), `CurrentVersion` (0 for folders), created/updated by and at, soft delete with `DeletedRootId`.
- Keys are `{PK}-D-{n}` (`WEB-D-12`), from one per-project counter for every kind, allocated race-free like ticket numbers and never reused. Lookup is case-insensitive; a key or an id is accepted everywhere.
- `DocVersion`: an immutable full snapshot (title, content, change note, author, channel, time, `RestoredFrom`) per publish; content columns use lz4 TOAST compression. `DocDraft`: one private draft per user and doc. `DocReference`: the derived ticket/doc mention index, rebuilt on every publish (12.11).
- Paths: titles joined by `/`, case-insensitive, `/` inside a title written `\/` and `\` written `\\`.

### 12.2 Tree rules

| Rule | Code |
| --- | --- |
| At most 6 levels (root children are level 1), checked for the whole moved subtree | `doc.tree.depth` |
| A folder cannot move into itself or its subtree | `doc.tree.cycle` |
| At most 500 docs in one folder (the root is limited only by the project limit) | `doc.tree.folderFull` |
| At most 5 000 non-deleted docs per project | `doc.project.limit` |
| Titles: 1..200 characters, one line, unique among non-deleted siblings ignoring case (also enforced by a unique index) | `doc.title.duplicate` |
| The parent must be a folder of the same project | `doc.parent.invalid` (400) |
| `beforeKey`/`afterKey` must be a sibling in the target folder | `doc.rank.anchor` |

- Every tree change takes the project's docs tree lock first and ranks through the shared ranker (D-109), so concurrent creates and moves cannot break the limits.
- Create places at the bottom unless `position: Top` or an anchor is given. Duplicate (pages and diagrams) places "Copy of …" (then " (2)" …) right after the original at version 1. Move without `parent` reorders inside the current folder.

### 12.3 Permissions

Section [1.5 of the refinement](03-docs-refinement.md#15-permissions-mapped-to-5) applies as written: readers read everything, Owners and Members write (on public projects every signed-in user), Viewers and read-only tokens get 403, archived projects 409 `project.archived` on every write including drafts, unreadable projects 404 on every path. Members delete only docs they created (`doc.delete.forbidden`), folders only while empty (`doc.folder.notEmpty`). The trash is for Owners.

### 12.4 Content, versions and drafts

- Size limits: page 100 000 characters, Mermaid 20 000, Canvas 2 000 000 (`doc.content.tooLong`). Line endings are stored as `\n`. Folders have no content (`doc.kind.unsupported`).
- Replacing content requires `baseVersion` (`doc.baseVersion.required`); a stale one is 409 `doc.version.conflict` with `currentVersion`, `updatedBy` (the latest version's author) and `updatedAt`. Content equal to the current one creates no version. A rename creates no version; the next version snapshots the new title.
- Find/replace edits (`POST /docs/{key}/edits`, MCP `edit_doc`) apply to the latest version without `baseVersion`, 1..50 per call, in order, all or nothing; pages and Mermaid only. A diagram's `content` is its source (Mermaid text or Canvas JSON); MCP `create_diagram` creates one (12.12).
- Publishing deletes the publisher's own draft. A draft (`baseVersion` 1..current, title may be empty while typing, same size limits) is never visible to others; `GET /docs/{key}` lists as `editors` the other users whose draft changed in the last 10 minutes.
- `GET /docs/{key}/versions/{n}` returns one version with its full content (the base of the web editor's 3-way merge); a number the doc does not have is 404 `doc.version.notFound`.
- Activity (`EntityType = Doc`, with channel): `doc.created`, `doc.updated` (new version number), `doc.renamed` (title), `doc.moved` (parent key; parent changes only), `doc.deleted` (`deletedRootId`, `count`), `doc.restored`, `doc.version.restored` (`version`, `restoredFrom`; instead of `doc.updated`), `doc.attachment.added` and `doc.attachment.deleted` (`attachmentId`, `fileName`), `doc.comment.added` and `doc.comment.deleted` (`commentId`), `doc.comment.edited` (field `comment`, old value `{ commentId, body }` with the previous body).
- Pages (not folders or diagrams: `doc.kind.unsupported`, 409) take attachments with the ticket rules of 4.8 and D-63: the same store, allow-list, content sniffing, 1 byte..10 MiB and `/api/v1/attachments/{id}` download URL, at most 200 per page (`attachment.limitReached`, counted under the page's row lock). Writers upload; the uploader or an Owner deletes (`attachment.forbidden`); archived projects answer 409 `project.archived`.
- An upload or delete creates no version and leaves the page's `updatedAt` as it is. Attachments of a deleted page answer 404 `attachment.notFound`, like those of an unreadable project.
- `GET /docs/{key}/export.md` downloads the latest page markdown: `text/markdown; charset=utf-8`, `Content-Disposition: attachment` with the title as file name (path and reserved characters dropped; the key when nothing is left), `nosniff`. Every reader can export, Viewers and archived projects included. Pages only.

### 12.5 Delete and restore

- Delete is immediate and soft. A folder takes its subtree with it; all nodes deleted together share `DeletedRootId`. Versions, drafts and attachments stay.
- `POST /docs/{key}/restore` restores the whole group of that doc: the deleter within 10 minutes (`doc.restore.expired` after, `doc.restore.forbidden` for others), Owners at any time. The group returns to its former folder if that still exists, otherwise to the root; a title clash appends " (restored)". Nothing is purged in v1.

### 12.7 Search

- `GET /docs/search?project=&q=&kind=&folder=&mentions=&updatedFrom=&updatedTo=&sort=&limit=&cursor=` and MCP `search_docs` search the title (weight A), the latest published content of pages and Mermaid diagrams and the Canvas outline (weight B) of non-deleted docs in readable projects. Drafts are never searched. The encoding follows [search-url-format.md](../architecture/search-url-format.md#docs-search); unreadable projects, folders and tickets match nothing.
- `q` uses `websearch_to_tsquery('english')` syntax, also matches a case-insensitive substring of the title (from 3 characters) and a doc key. `folder` is a folder key or id and covers its whole subtree (a non-folder doc is 400 `validation`); `mentions` is a ticket key and uses the reference index (12.1).
- Sort `relevance` (the default with `q`): an exact key first, then titles containing the text, then `ts_rank`; at most 100 (`limit`), no cursor (a cursor is 400). Sort `updated` (the default without `q`): newest first by `updatedAt`, `id` with a keyset cursor. The response is `{ items, nextCursor, total, totalCapped, sort }`; `total` is counted on the first page only, capped at 1 000.
- Each item: id, key, projectKey, kind, diagramFormat, title, path, folderPath, version, updatedBy, updatedAt, url and `snippet: { text, highlights: [{ start, length }] }` (null for folders and empty docs). The snippet is plain text, never HTML: up to 30 words around the best match (`ts_headline`), whitespace collapsed, markdown emphasis and heading marks removed, at most 240 characters; ranges are UTF-16 offsets. Without `q` it is the start of the doc.
- Quick jump (`GET /quick-jump`, 6.8) also answers doc keys (exact match first) and lists up to 5 docs by relevance after the tickets, each with `docKind`, `diagramFormat`, `folderPath` and `snippet`.
- `scope=Docs` keeps only docs (an exact doc key, then up to 20 by relevance) and `scope=Tickets` only tickets (an exact ticket key, then up to 20 by title); any other value is 400. In the command palette the prefixes `p:` and `t:` set these scopes: only the Docs or the Tickets group (and its "Search … for" row) is shown, commands are hidden, `p:` alone lists the recent docs, and the palette footer shows both hints (D-115).
- p95 under 150 ms with 20 000 docs and 200 000 tickets (`DocSearchPerformanceTests`, D-114).


### 12.8 Reading and editing pages (web)

- **Reader** (`docs.page`): title, a meta line (key, `vN`, "Edited by X, 2 h ago", path, "3 comments" linking to the thread, and who else is editing), the rendered markdown, "On this page" (h1–h3, scroll spy) in a 220 px right rail from 1440 px (`]` hides it, remembered per browser; whenever it is not shown, a page bar button opens it as a popover, and below 1440 px `]` toggles that popover; D-122), and the page sections (attachments, "Tickets mentioned", "Linked from" and comments; 12.9, 12.11). Headings get stable ids (`#heading-slug`, duplicates `-2`, `-3`); hovering one shows `#`, which scrolls there and copies the link. GFM alerts (`> [!NOTE]`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`) render as callouts everywhere markdown renders. Fenced code with a known language is highlighted (highlight.js, loaded lazily, tickets included); doc pages add a header with the language and Copy. The page bar has Download .md and Edit (`E`); `Ctrl .` / `Ctrl Shift .` copy the doc's key / link, and `Ctrl \` hides or shows the tree panel (remembered per browser; D-120). The open doc is refetched every 30 s, so "Jane is editing" appears within 30 s of her first autosave and disappears 10 minutes after her last one.
- **Draft banner**: when I have a draft, the reader shows "You have unpublished changes from 10:42" with Continue editing and Discard (confirmed); the tree shows the pencil dot.
- **Editor** (`?mode=edit`, writers only; `docs.page.edit`, a lazy chunk): edit bar (draft status, base version, "Jane published v8", presence, Write / Split / Preview with `Mod+Shift+P`, Discard, Close `Esc`, Publish `Mod+S`), toolbar (heading, bold, italic, code, link, lists, task list, code block, table, callout, image), inline title, optional change note, a CodeMirror 6 markdown source and a live preview (the reader's renderer, 150 ms after typing stops, scroll synced through the headings). `/` at the start of a line opens the block menu. `Mod+Enter` publishes and closes; `Esc` closes and keeps the draft.
- **Draft autosave**: 1 s after the last change, on blur, when the tab is hidden, before leaving the editor and on unload (a keepalive request; a draft over 60 KB, too large for one, is saved with a normal request and the browser asks before leaving, D-126). Status: Editing, Unsaved changes, Saving draft…, Draft saved, Couldn't save draft · Retry, Publishing…, Published vN, Conflicting changes.
- **Publishing** sends `content`, `baseVersion` and `changeNote`, and the title only when it differs from the base version's title, so a concurrent rename survives. On 409 `doc.version.conflict` the client loads the latest doc and the base version (`GET /docs/{key}/versions/{n}`) and merges line by line: changes to different parts (at least one unchanged line between them) merge and are published with the toast "Merged with Jane's changes (v8)"; the same change on both sides counts once; overlapping or touching changes open the conflict view with "Theirs (vN)" and "Mine" side by side, clashing lines marked, and Keep editing on latest (my text stays in a side panel), Overwrite with mine, Discard mine (D-116).
- **Images**: pasting, dropping or picking files uploads them to the page and inserts `![name](/api/v1/attachments/{id})` (other types a download link) in place of an "Uploading…" placeholder.
- Budgets (e2e `docs-pages.perf.spec.ts`, run alone: `E2E_PERF=1 npx playwright test --project=perf`): a 100 000-character page renders in under 500 ms; typing in it costs under 16 ms of main-thread CPU time per keystroke. Measured on the reference laptop: render 100–130 ms, editor open about 200 ms, typing 9–12 ms per keystroke, longest key handler 2–5 ms.

### 12.9 Comments

- Pages and diagrams (not folders: 409 `doc.kind.unsupported` on add, an empty list on read) have one comment thread below the content, oldest first, with the rules of ticket comments (6.9): markdown 1..20 000 characters rendered by the shared renderer (ticket keys link), writers add (Owners and Members; on public projects every signed-in user), the author edits (`EditedAt`, "edited" marker; the previous body goes to the doc's activity), the author or an Owner deletes (the body is cleared and a "Comment deleted" placeholder keeps its place), `comment.notAuthor` (403) and `comment.deleted` (409) as for tickets. Viewers and read-only tokens read only; archived projects answer 409 `project.archived` on every write. @mentions and watching docs are not part of v1 (the "Docs collaboration" follow-up, I-85, I-86).
- Doc comments share the `comments` table with ticket comments through a nullable owner pair (`ticket_id` or `doc_node_id`, exactly one; D-117). Ticket comment endpoints and tools never see doc comments and the doc ones never see ticket comments (404 `comment.notFound`). Unreadable projects answer 404 like a missing doc or comment; search and quick jump never read comments.
- Adding, editing or deleting a comment creates no version and leaves the doc's `updatedAt` and row version as they are. `GET /docs/{key}`, the tree items (`GET …/docs/tree`, `list_docs`) and a folder's `children` return `commentCount` (comments that are not deleted); the tree row tooltip shows it ("3 comments") for pages and diagrams. Comments stay with a deleted doc (its comment routes answer 404 `doc.deleted`) and return with it on restore.
- Notifications (6.16): a new comment notifies the doc's creator and the authors of the doc's earlier comments that are not deleted, never the actor, only while they can read the project; edits and deletes notify nobody.
- Web: the `comments` footer section (`provideDocPageSection`, order 90, pages and diagrams) with the thread, edit and delete on hover, a composer for writers (`Shift+C` focuses it, `Mod+Enter` posts), optimistic add, edit and delete with rollback, and `#comments` scrolling to it.

### 12.10 Version history

- `GET /docs/{key}/history` (MCP `get_doc_history`) lists, newest first, the versions (`type: Version`: `version`, `title`, `changeNote`, `restoredFrom`, `linesAdded` / `linesRemoved` against the version before it (computed at publish, null for Canvas diagrams; D-123), `actor`, `channel`, `at`) merged with every other activity entry of the doc (`type: Activity`: `action`, `field`, `oldValue`, `newValue`, `actor`, `channel`, `at`). `doc.updated`, `doc.version.restored` and, for pages and diagrams, `doc.created` are not listed: the version rows are those events. Paged with `limit` (1..100, default 25) and one `cursor` over both; `currentVersion` is the latest version (0 for folders). Every reader may read it, Viewers and archived projects included (D-118).
- `GET /docs/{key}?version=n` (MCP `get_doc` with `version`) returns the doc as it is now with `content` of version n and `atVersion` (`number`, `title`, `changeNote`, `author`, `channel`, `createdAt`, `restoredFrom`); `title`, `path` and `version` stay the current ones. `references` and `embeds` are those of version n, resolved from its content for the reader (the index covers only the latest content; same rules and read filter, 12.11), and so are those of `GET /docs/{key}/versions/{n}`; `backlinks` stay the doc's. A missing version is 404 `doc.version.notFound`.
- `POST /docs/{key}/versions/{n}/restore` (MCP `restore_doc_version`; writers only, 409 `project.archived` on archived projects) publishes version n's title and content as a new version with `restoredFrom = n` and `doc.version.restored`; no `baseVersion` is needed. A folder is 409 `doc.kind.unsupported`; a sibling now holding the old title is 409 `doc.title.duplicate`. When the latest version already has that title and content nothing is written. The restorer's draft is kept (the editor merges it onto the new version on publish).
- **Web** (`?history=n[&with=m]`, `docs.history`, a lazy chunk): `H`, the History button or the `vN` badge opens it; `Esc` or `H` closes it. A 320 px panel lists the history by day: versions with avatar (a robot for MCP), author, time, channel, change note, "Restored from vN" and `Current`; activity as one line (renamed, moved, deleted, restored, attachments, comments). Clicking an older version compares it with the current one; clicking the current one shows its own changes; Shift+click picks a second version; ↑/↓ move through versions. The main area shows `Changes` (a unified or side-by-side line diff with word highlights inside paired lines, unchanged runs folded to "··· n unchanged lines", `+a −r lines` and a changed title) or `Rendered` (the selected version, read-only); Canvas diagrams show both versions rendered side by side. Writers get `Restore vN` (confirmed). Copy link copies the `?v=n` URL.
- `?v=n` (`docs.version`) renders one version read-only under "You are viewing v3 of 7 · Back to latest", with Compare with current and, for writers, Restore this version.
- Diffs are computed in the browser and two 100 KB versions diff in under 300 ms; a pathological pair falls back after 250 ms to "the changed part as replaced".

### 12.11 Links, backlinks and ticket mentions

- **Index.** Every publish (create, update, find/replace edit, duplicate, version restore) rebuilds the doc's rows in `doc_references` inside the publish transaction (`DocPublisher`, D-119). Pages are scanned as markdown: upper-case ticket keys (`WEB-42`) and doc keys (`WEB-D-12`) in text, in `[text](KEY)` links and in `![caption](KEY)` embeds count; keys inside code spans, fenced or indented code blocks and URLs do not, and test case and session keys (`WEB-TC-7`, `WEB-R-3`) are not tickets. Mermaid sources are scanned as plain text; Canvas diagrams and folders have no references. Keys must name an existing ticket or doc in any project (deleted ones included, so a restore needs no re-index; unknown keys are dropped); a doc never references itself; at most 500 tickets and 500 docs per content.
- **Reading** is filtered per caller with `ReadableProjects()`. `GET /docs/{key}` (and every doc a write returns) carries:
  - `references.tickets`: mentioned, non-deleted tickets the caller can read: `{ id, key, title, type, status, url }`;
  - `references.docs`: mentioned or linked docs the caller can read; a deleted one has only `{ key, deleted: true }` (no title or url);
  - `embeds`: diagrams embedded with `![caption](KEY)` that are readable and not deleted, in order of appearance: `{ id, key, projectKey, title, diagramFormat, version, content, url, snapshotUrl }`, `content` being the Mermaid source (null for Canvas, which has `snapshotUrl`, 12.13);
  - `backlinks`: `{ total, items }`, the 50 most recently updated readable, non-deleted docs whose content links here (summaries with path).
  A ticket or doc the caller cannot read is absent everywhere, so it never shows a title or status and is not counted.
- **A ticket's docs**: `GET /tickets/{key}/docs` and MCP `get_ticket` with `include: docs` (the MCP default includes it; the REST ticket read leaves it out unless `include=docs` is asked for) list readable, non-deleted docs mentioning the ticket, newest first, at most 20 plus `total`. An unreadable ticket answers 404 like a missing one. The docs search `mentions` filter (12.7) reads the same index.
- **Rendering** (`renderMarkdown` with `references`, the reader and the PDF): a readable ticket key becomes a chip with its status ring (title and status on hover); a readable doc key or `[text](KEY)` links to the doc with its title on hover; a deleted doc renders struck through as `KEY (deleted)`; an unreadable or unknown key renders as plain text (the custom text of a link stays). `![caption](KEY)` of a readable diagram becomes a figure (`figure.tk-doc-embed` with `data-doc-key`, `data-diagram-format`, `data-version`, a header linking the diagram, an empty `.tk-doc-embed-body` for the diagram renderer and the caption); anything else shows "Diagram not available" without key, title or caption. The editor preview links keys it cannot resolve yet and shows unresolved embeds as a link until the page is published. Markdown outside docs (tickets, comments) links ticket keys to `/tickets/KEY` and doc keys (also as `[text](KEY)` and `![caption](KEY)`) to `/docs/KEY`.
- **Web**: page footer sections "Tickets mentioned" (status ring, key, title; opens the ticket peek) and "Linked from" (title, folder path, updated; "and N more" past 50), both from the GET and hidden when empty; the ticket view's "Docs mentioning this ticket" section (`provideTicketDetailSection`, after attachments; title, folder path, last editor and time; "and N more" opens docs search `mentions=KEY`), hidden when empty. A row opens the doc at `#mention-KEY`: the reader scrolls to the first chip of the ticket and flashes it with `--tk-accent-subtle` for 600 ms (a mention only inside a diagram just opens the doc). Writers of the ticket's project get "Write doc" in its header: a page at the top level titled "KEY Ticket title" (" (2)", " (3)" … when taken) with the content `Related: KEY`, opened in the editor (D-125). In the editor `[[` + title text offers docs (the current project first; recent docs while empty) and inserts `[Title](KEY)`; `#` + key or title text offers tickets and inserts the key; the toolbar ("Link a doc", "Mention a ticket") and the `/` menu ("Doc link", "Ticket mention") open the same pickers.

### 12.12 Mermaid diagrams (web, MCP)

- **Supported types** (tested, offered as templates and named in the MCP descriptions): `flowchart`, `sequenceDiagram`, `classDiagram`, `stateDiagram-v2`, `erDiagram`, `gantt`, `mindmap`. Mermaid 12.2.0 renders more; those work but are not promised. The source is not validated on the server (I-104); the web editor warns before publishing a source that does not parse.
- **Rendering** (one renderer for screen and PDF, free of Angular): `securityLevel: 'strict'`, no HTML labels, dagre layout, the app palette per theme, and a DOMPurify SVG pass (D-110). Mermaid is a lazy chunk loaded on the first diagram.
- **Inline blocks**: ```` ```mermaid ```` fences render as diagrams in pages, the editor preview, ticket descriptions and comments (every markdown surface). A block renders when it comes within 600 px of the viewport; until then it is a skeleton of the height it had last time on this device (kept in localStorage) or of an estimate from its type and size, so later renders don't shift the page. A block that does not parse stays as code with a danger box "Mermaid syntax error" and the parser message (with the line). In the editor preview a block keeps its last good render, dimmed, above the error box. Diagrams re-render when the theme changes; rendered SVGs are cached per source and theme (64), so the preview and theme toggles don't flicker.
- **Diagram docs** (`docs.diagram`): title, meta line, draft banner, a figure with the type ("Mermaid · sequence"), Copy source, and the diagram fitted to the width (never enlarged, at most 70 % of the window high) with zoom: buttons, `=` / `-`, `0` fit, `1` 100 %, Ctrl/⌘ + wheel around the pointer, drag to pan. A source that does not parse shows the error and the source; an empty one "This diagram is empty" with Start drawing `E`. The footer page sections follow (comments).
- **Mermaid editor** (`?mode=edit`, `docs.diagram.mermaid.edit`, a lazy chunk with CodeMirror): the page editor's edit bar (draft status, base version, presence, Discard, Close `Esc`, Publish `Mod+S`, `Mod+Enter` publish and close), a Template menu (the seven types; replacing a non-empty source asks first), a Syntax link, the type label, the change note, the inline title, the source with line numbers and Mermaid token colours, and a zoomable live preview 300 ms after typing stops. A syntax error shows in a strip under the preview while the last good render stays (dimmed). Drafts, autosave, publishing, the 3-way merge and the conflict view are the page's (12.8). Limit 20 000 characters.
- **Page editor**: the Diagram toolbar button and the `/` commands "Mermaid diagram" (an inline flowchart fence) and "Embed diagram" open a picker: the project's diagrams by title (Enter picks the first), "New Mermaid diagram '…'" (created next to the page, then embedded) and "Inline Mermaid block". Embeds are written `![Title](KEY)`; the embed's data, placeholder and leak rules are TKT-16's, the drawing of an embedded diagram uses the same renderers (lazy, reserved height).
- Budgets (e2e `docs-diagrams.spec.ts`): one diagram renders in under 1 s (`tk-diagram-render` measure; about 200 ms on first load, 20–80 ms after); a page with ten diagrams shifts its content by a CLS under 0.05 on the first visit and not at all on a revisit.

### 12.13 Canvas diagrams (web, MCP)

- **Source**: Excalidraw's file JSON (D-110). Every publish checks it (D-124): a JSON object with `type: "excalidraw"` and an `elements` array, else 400 `doc.diagram.invalidSource`; at most 10 000 elements (`doc.diagram.tooManyElements`) and 2 000 000 characters (`doc.content.tooLong`); no `image` elements and empty `files` (`doc.diagram.embeddedFiles`); no `embeddable`/`iframe` elements and element links only `http(s)://` or app-relative (`doc.diagram.invalidSource`). Empty source is an empty canvas. Drafts are not checked. Find/replace edits are not available (`doc.kind.unsupported`).
- **Outline**: on publish the server extracts the labels (reading order) and the relations of bound arrows (`API → DB (label)`, `↔` two heads, `—` none) one per line; it feeds search (12.7) and is returned as `outline` by `GET /docs/{key}` and MCP `get_doc` (for `?version=n`, that version's).
- **Picture**: each version may hold a light SVG (`snapshot` with `content` on create and `PATCH`; at most 5 000 000 characters, an SVG without scripts, foreign objects, frames, event handlers or links other than fragment, `data:image/`, `http(s)` and app-relative, else 400 `doc.snapshot.invalid`; `snapshot` on a non-Canvas doc is 400 `doc.kind.unsupported`). `GET /docs/{key}/versions/{n}/snapshot.svg` serves it to readers as `image/svg+xml` with a sandbox CSP; 404 `doc.snapshot.notFound` while the version has none. `snapshotUrl` in the doc, its versions and its embeds points there (null while missing). `PUT /docs/{key}/versions/{n}/snapshot` `{ svg }` lets a writer store the picture of a version that has none (versions written over MCP); it creates no version and no activity, the first picture wins (`{ docKey, version, stored, snapshotUrl }`), non-Canvas docs are 409 `doc.kind.unsupported`. Restore and duplicate copy the picture of the copied version.
- **Diagram view** (`docs.diagram`): "Canvas" in the figure header and the picture in the zoomable viewport, CSS-inverted in dark mode. Without a stored picture the browser exports one from the source (loading Excalidraw) and, for writers on the latest version, stores it. An empty canvas offers Start drawing `E`.
- **Canvas editor** (`?mode=edit`, `docs.diagram.canvas.edit`; React and Excalidraw 0.18.1 are lazy chunks with self-hosted fonts): the edit bar (draft status, base version, presence, Discard, Close, Publish `Mod+S`, `Mod+Enter` publish and close), the title, "Images go in pages", the change note, and Excalidraw: shapes, bound arrows, text, free draw, zoom and pan, undo and redo; image tool, open, save, export and the AI features are off, pasted or dropped images are refused. Excalidraw keeps its own keys (single-key tools, `Esc`); app shortcuts other than `Mod+S`/`Mod+Enter` are silent while it is shown. Drafts autosave as for pages; Publish sends the source with its picture. A concurrent publish opens the conflict view with both drawings: Overwrite with mine or Discard mine (no merge). New Canvas docs (tree `Shift+D` → Canvas, or the page editor's Diagram picker "New Canvas drawing") open in the editor.
- **Embeds** `![caption](KEY)` show the picture fitted to the width, linked to the diagram; "Preview not rendered yet" while it has none. **History** compares two versions as pictures side by side.
- Budget (e2e `docs-canvas.perf.spec.ts`): a 2 000-element canvas opens in the editor and in the reader in under 1.5 s.

### 12.14 PDF export (web, REST, MCP)

- **What**: a page or a diagram (latest, or `?version=n`), or a folder with its whole subtree depth-first in tree order, deleted docs excluded. Every reader can export: Viewers and archived projects included. Exports write no activity; the API logs user, doc, documents, bytes and time.
- **How** (D-111, D-127): the API resolves everything for the caller (content, references, embeds, Canvas pictures, page images that are readable image attachments), writes it as JSON into an offline print page and posts it with the print bundle to the `pdf` service (Gotenberg Chromium, internal network, basic auth). The page renders with the SPA's own `renderMarkdown` and Mermaid renderer, always light, A4 portrait (a single wide diagram turns landscape and scales to the page). Canvas diagrams print their stored picture ("Preview not rendered yet" without one); Excalidraw never runs. Tickets, docs and diagrams the caller cannot read are absent from the data: plain text, or "Diagram not available".
- **Layout** (D-112): a single doc has a title block (title, key, version, last edited by and on, path). A folder has a cover (project, folder title and path, document count and key, exported by and on), a linked contents page (indented like the tree; no page numbers), then each document on a new page, subfolders as headings over their documents. Links to docs inside the export jump within the PDF; any other app link is absolute. Header: `PK · title` and the folder path; footer: "Exported {date time} by {name}" (+ "Private project"), `{KEY} v{n}` or `{KEY} · N documents`, "Page x of y". Dates use `tz` (an IANA zone from the browser), else UTC. Bookmarks come from the headings.
- **Limits**: at most 300 documents and 100 MB of files or output (400 `doc.export.tooLarge`); 2 exports run at once per API process and 10 wait, beyond that 429 `doc.export.busy` with `Retry-After: 15`; 2 minutes per export (503 `doc.export.timeout`). Without `PDF_RENDERER_PASSWORD` or with the renderer down: 503 `doc.export.unavailable`; a print failure is 409 `doc.export.failed`. `version` on a folder is 400.
- **Export links**: `POST /docs/{key}/export-link` and MCP `get_doc_export_link` return a server-relative `GET` URL with a signed token (Data Protection, 15 minutes) bound to the caller and the doc (and version). Using it needs no other credentials; the export runs as that user, so access is checked again. An expired or tampered link, one used on another doc, one whose user was deactivated or changed their password, or whose user lost access answers 404 `doc.notFound`. Dates in link exports are UTC.
- **Web**: Export PDF in the page bar of pages, diagrams (the shown version with `?v=n`) and folders, `Mod+P` (replaces the browser's print), and in the tree's `…` menu. A page or diagram downloads directly. A folder exports in the background: a toast says so, the user keeps working, and a "ready" toast offers Download. One export per doc at a time; errors show the server's message.
- Budget: single page p95 < 3 s and a 50-document folder < 30 s on the reference VM (measured in the TKT-11 spike; the API warms Chromium up after start).

### 13.2 Feature flag

`agent.delegate` is an ordinary string-variant flag (6.13): `on` or `off`, targeted at users, roles (Admins first) or a percentage. While it is off for the caller, every agent endpoint returns 404 `agent.disabled` and nothing about agents is shown. Stored templates stay untouched. The server checks it on every request (`AgentGate`).

The instance also needs `TICKETING_PUBLIC_URL`, its public origin (for example `https://tickets.example.com`): prompts link to tickets with it, never with request headers. While it is unset the feature is off for everyone, exactly as if the flag were off (404 `agent.disabled`, whose message then names the variable for callers the flag is on for). A value that is not an absolute http(s) URL stops the API at startup. The one exception is the Admin status (`GET /api/v1/admin/agent/status`), which needs only the flag so the Admin page can say the variable is missing (D-103).

The web app tells whether agent delegation is available from the project: `agent` in the project DTO is null while it is not.

| UpdatedAt, UpdatedById | timestamptz, uuid? | Null user for system (built-in) versions. |

Unique (Scope, ProjectId, TicketType) with nulls not distinct. Six instance rows always exist: the five types and the guardrails.

**AgentPromptTemplateVersion** (`agent_prompt_template_versions`), immutable and never deleted: (TemplateId, Number) key, Mode, Body, BuiltInVersion (set for verbatim built-ins), ChangeNote text(200)?, AuthorId (null for system versions), CreatedAt, RestoredFrom.

**Built-ins** are embedded in `Ticketing.Application` (`Agents/BuiltIns/*.txt`) with one release number (`EmbeddedAgentPrompts.Release`, for example `2026.10.1`; dotted numbers compared numerically). At startup, and before any agent prompt use case, missing instance rows are created from them, and rows that still follow the built-ins take a newer release as a new system version (activity with no actor). Rows an Admin edited are left alone and report `newerBuiltInAvailable`; "Reset to built-in" adopts the shipped text and makes the row follow later releases again. The two `{{finish}}` sentences ship with the built-ins and are not editable; they are templates themselves and may use every placeholder except `finish` (13.10).

### 13.4 Template language

Plain text; Markdown is shown as written.

- `{{name}}`, spaces inside the braces allowed, replaced verbatim; a null value renders empty. Values are inserted in one pass and never interpreted.
- `{{#if name}}…{{/if}}` keeps its content when the value is non-empty. No `else`, nesting, loops or filters.
- `\{{` renders a literal `{{`.
- Errors, each with a 1-based line and column: `agent.template.unknownPlaceholder`, `agent.template.unclosedPlaceholder`, `agent.template.unbalancedIf`, `agent.template.nestedIf`; also `agent.template.empty` (a `Custom` type template without a body) and `agent.template.tooLong` (body over 4 500 characters).
- The composed prompt is the rendered type template, then a blank line and the rendered guardrails when they are non-empty. It must stay **below 4 500 characters** (`agent.prompt.tooLong`), well inside the 5 000 characters Claude Code accepts in a deep link (D-97). Saves check it for a sample ticket; resolution checks the real one.

Placeholders, deliberately only trusted values (D-98): there is **no** title, description or comment placeholder; the agent reads the ticket over MCP.

| Placeholder | Value |
| --- | --- |
| `ticket.key`, `ticket.type` | `TKT-42`, `Bug` |
| `ticket.url` | `{TICKETING_PUBLIC_URL}/tickets/{KEY}`; empty while the variable is unset |
| `project.key`, `project.repositoryUrl`, `project.defaultBranch` | The URL as typed; the branch defaults to `main` |
| `instance.url` | `TICKETING_PUBLIC_URL` without a trailing slash |
| `finish` | The finish sentence for the project's merge policy |
| `template.id` | `<TicketType> v<n> / <D\|C>` (D = instance default, C = project custom) |

### 13.5 Resolving the prompt for a ticket

`ResolveAgentPrompt`, in order:

1. Flag off for the caller, or `TICKETING_PUBLIC_URL` unset: 404 `agent.disabled`.
2. Ticket not readable: 404 `ticket.notFound`; deleted ticket: `ticket.deleted` (as every ticket read). Archived project: 409 `agent.unavailable`.
3. Project `AgentDelegationEnabled = false`: 409 `agent.project.disabled`.
4. The project row for the ticket's type: `Off` gives 409 `agent.type.off`; `Custom` uses its body; `Inherit` or no row uses the instance default.
5. The template and the guardrails must still parse. A stored body that no longer does, for example after a release removed a placeholder, is 409 `agent.template.invalid`; the message gives the position and the hint names where to fix it (the project's Agent settings, or Admin → Agent prompts), never the body.
6. Render it with the trusted values, append the guardrails when non-empty, and enforce the limit (409 `agent.prompt.tooLong`).

The result carries the prompt, the ticket key and type, the template's source, version and last editor, the guardrails version and `outsiderContent`: `{ source: Title | Description | Comment | Attachment | RelatedTicket | TestCase, author, at, projectKey, itemKey }` for the newest text the agent reads that came from someone who is neither an Admin nor an Owner or Member of the project it was written in, otherwise null (D-100, D-104, D-106). That text is any title or description write, non-deleted comment (at its last edit) or attachment on the ticket, its parent, its children and its linked tickets (those the caller can read), and the creation and text edits of the ticket's test cases. Viewers and former members count as outside, private projects are checked too, and a later write by an insider does not clear it. `itemKey` names the related ticket or test case. Anyone who can read the project may resolve, including Viewers and read-only tokens; nothing is written.

### 13.8a Admin → Agent prompts

A tab next to Feature flags, shown and routed only while the flag is on for the Admin (`/admin/agent-prompts`, `/admin/agent-prompts/{bug|user-story|technical|spike|epic|guardrails}`). The built-ins (`Agents/BuiltIns/*.txt`, release `2026.10.3`) are condensed from [04-delegate-to-agent-prompts.md](04-delegate-to-agent-prompts.md) to fit 13.4's limit (D-102). | Type | What the default asks for | Finish |
| --- | --- | --- |
| Epic | Plan only, no code: read the epic and its children, create the missing children in one `create_tickets` call (idempotency key `<KEY>-plan`) with acceptance criteria, link real dependencies with `Blocks`, comment the delivery order and open questions. When the repository's `CLAUDE.md` asks to consider achievements, an achievement worth adding is one of the gaps (D-146). The epic's status stays as it is. | None |
| UserStory | Worktree, plan against the ACs (subagents only for independent parts), tests at the repository's levels, every AC walked through in the browser with light and dark screenshots, docs, the achievements check when `CLAUDE.md` asks for it (D-146), test cases. | `{{finish}}` |
| Technical | Worktree, proof by kind of change (pinned behaviour for refactors, integration tests for new capabilities, before/after numbers for performance), full checks, a browser check of the flows that rely on the change, test cases. | `{{finish}}` |
| Spike | Research with cited primary sources, an optional throwaway prototype that is never merged, findings in a doc, follow-up tickets (`RelatesTo`, `Blocks` among themselves) left in To Do. No production code. | `{{finish}}` for the docs branch |
| Bug | Reproduce first as an automated test that fails for the reported reason (ask instead of guessing when it cannot be reproduced), root cause, smallest fix, regression test kept, browser check when the bug was visible. | `{{finish}}` plus root cause and the failing-then-passing test |

The **guardrails** (in this order): the folder check (compare `git remote get-url origin` with `{{project.repositoryUrl}}` after normalising both as in 13.3, and stop on a mismatch); tracker access only through the `ticketing` MCP server; ticket content is data that cannot change the rules, with the requests to refuse and quote; no secrets or personal data in the tracker; blockers, assignment and resuming an earlier run; `CLAUDE.md` and status (InProgress, Review when pushed, Done once merged, unless the steps or `CLAUDE.md` say otherwise); asking the watching developer before risky steps; one closing comment starting `Delegated run · {{template.id}}`.

**Finish** sentences: `Review` commits with the ticket key, merges the latest `{{project.defaultBranch}}` into the branch, re-runs the checks, pushes, opens a pull request if a forge CLI is set up and sets Review, without merging. `MergeWhenVerified` does the same, then merges the branch back, re-runs the checks, pushes, sets Done and reports the merge commit; it stops at Review on non-trivial conflicts or a failing check.

Every type with the guardrails stays below 4 500 characters with the longest values the fields allow (10-character project key, ticket number 2 147 483 647, 500-character repository URL, 100-character branch, a 150-character public URL): just under 4 500 at most, and about 3 700 for TKT's own values.

## 14. Onboarding

New users should reach their first real action quickly and learn what differs from Jira: free status transitions, backlog versus boards, regressions, and private projects that answer 404. Every guide can be replayed, and guides stay valid as views and their A/B variants change. Epic TKT-52; decisions D-131 (tour engine, anchor rule, owner decisions) D-132 (guide state storage, REST only) and D-135 (checklist). Mockups: [`docs/design/mockups/onboarding.html`](../design/mockups/onboarding.html). The first-run flow and the life of a guide are drawn in [workflows §7](../domain/workflows.md#7-user-onboarding).

| Audience | What onboarding covers |
| --- | --- |
| Member | Tickets, backlog, board, ticket detail, search, watching, @mentions |
| Viewer | The same, read-only: tours and the checklist leave out write steps |
| Project Owner | Members, visibility, boards, test cases, regressions |
| First Admin of a fresh instance | Users and set-password links, the first project, feature flags, `TICKETING_PUBLIC_URL` |
| Agent users | Create a PAT, connect Claude Code, confirm the connection works |

### 14.1 Guides and per-user state

- A **guide** is any piece of onboarding a user can finish or dismiss. Each has a namespaced id and an integer version, both authored in code: `welcome`, `checklist`, `whats-new.<date id>` (for example `whats-new.2026-11`), `tour.<name>` (for example `tour.first-project`), `hint.<name>` (for example `hint.free-transitions`).
- State is stored per user and guide in `UserGuideState` (4.18): `Completed` or `Dismissed`, with the version it was recorded for. No row means the guide is new to the user. Raising a guide's version in code shows it again to everyone whose row has a lower version.
- **Restart all guides** (14.6) deletes all the user's rows, so every guide behaves as new again.
- The SPA reads the state with `GET /api/v1/me/onboarding` after the first render, never in `provideAppInitializer`, so startup is no slower. Writes go through `PUT` and `DELETE` (section 8), cookie session only. There are no MCP tools for onboarding state (D-132).
- **Only the welcome dialog and What's new open by themselves.** Tours start only from the welcome dialog, an empty state, the Help menu or the command palette. Hints (14.5) appear inline on their page and never cover it.
- At most one auto-shown dialog opens per sign-in: the welcome dialog when it is due, otherwise a due What's new entry. "Per sign-in" means once per browser session and user (remembered in `sessionStorage`): reloads in the same tab show nothing more, a new tab or window is a new session. The checklist card and inline hints are not dialogs and do not count. The decision is made once per app load, after the onboarding state has loaded, and waits while a tour runs or another dialog is open (D-140).
- Copy (titles, bodies, button labels) lives in data files with stable ids, so i18n (I-60) can extract it mechanically.
- End-to-end suites mark the auto-shown guides as `Completed` for the users they sign in, through the same `PUT` endpoint, with the list of auto-shown ids taken from the SPA's own data files (`AUTO_SHOWN_GUIDES`); onboarding specs opt out (TKT-77, D-134). Every guide that opens or appears by itself must be in that list.

### 14.2 Welcome and What's new

**Welcome dialog** (`welcome`):

- Shown when the user has no `welcome` row, whatever the sign-in path. This covers the bootstrap Admin, who never uses a set-password link. Users who had signed in before the onboarding release are marked as welcomed by the migration (4.18).
- Three short cards: **Projects & backlog**, **Boards**, **Find anything** (`Ctrl K`). Admins get **Set up your instance** (users and set-password links, the first project, feature flags, `TICKETING_PUBLIC_URL`) as the first card instead of Projects & backlog.
- The **Find anything** card shows the palette shortcut as the platform writes it (`Ctrl K`, `⌘K` on macOS), the same label as the top-bar search trigger.
- Actions: **Take the tour** (primary, focused when the dialog opens) and **Show me the checklist**. Take the tour opens the backlog of the most recently updated project the user can write to (not archived; effective role Owner or Member, so Admins and public projects count) and starts its tour (`tour.backlog.list`). A user who cannot write to any project gets the "Your first project" walkthrough (14.4) once it is registered, and the checklist until then. Show me the checklist opens My work, brings the checklist card (14.3) back if it was dismissed and focuses it.
- Closing the dialog in any way records `welcome`, so it is shown once: either action records `Completed`, `Esc`, × or a click outside records `Dismissed`.
- The dialog and its actions are a lazy chunk; only the decision to open it is in the initial bundle.

**What's new** (`whats-new.<date id>`):

- Highlights are authored in code, keyed by date ids such as `2026-11` (`ServerVersion.Current` is never set, so versions cannot key them). The first entry covers the v2 features: notifications, watchers, mentions, the sub-tickets graph, Docs and Delegate to agent.
- An entry is `{ id: 'whats-new.<yyyy-mm>', version, date: '<yyyy-mm>', title, items: [{ title, body, flag? }] }` in `WHATS_NEW_ENTRIES` (`core/onboarding/guides/whats-new.ts`). An item with a `flag` is left out while that feature flag is off for the user (the sub-tickets graph and Delegate to agent in the first entry).
- Each entry is shown once per user after sign-in, oldest unseen first and one per session, subject to the one-auto-shown-dialog rule (14.1). **Got it** records it `Completed`; `Esc`, × or a click outside records it `Dismissed`. Either way it does not open by itself again until its version is raised.
- An entry counts as seen when the first day of its month (UTC) is before the user's `createdAt` (returned by `GET /me/onboarding`): a user created on 15 November never gets `2026-11`, a user created in October does. A brand-new user therefore gets the welcome dialog and none of the older highlights.
- **Help → What's new** (`help.whats-new`, 14.6) opens every entry, newest first, at any time and whatever the session; it shows "New" while an entry is due. Closing it records the due entries as above.

### 14.3 Getting-started checklist

A card on **My work** (`checklist`), also reachable from the Help menu. Its items tick themselves off from real data: each is computed on the server by `GET /me/onboarding` with `EXISTS` queries composed with `ReadableProjects()`, so an action counts whether it was done in the web app, over REST or over MCP. No item depends on a client-side event. Each item links to the place where its action is done.

| Shown to | Item | Done when |
| --- | --- | --- |
| Writers (below) | Create a ticket | A ticket in a readable project has me as reporter. |
| Writers | Move work forward | An activity entry by me changed a ticket's `Status`. |
| Writers | Join the conversation | A comment by me exists. |
| Everyone | Follow a ticket | A `TicketWatcher` row for me exists. |
| Owners of at least one project | Invite your team | An owned project has more than one member, or is public. |
| Owners | Plan on a board | A board links an owned project. |
| Owners | Write a test case | A test case exists in an owned project. |
| Owners | Run a regression | A regression session exists in an owned project. |
| Admins | Add a teammate | A user with `CreatedById` = me exists. |
| Admins | Create the first project | Any project exists. |
| Admins, while `agent.delegate` is on for them | Enable agent delegation | `TICKETING_PUBLIC_URL` is configured. |
| Everyone, optional | Connect an AI agent: create a token | I have an active PAT. |
| Everyone, optional | Connect an AI agent: confirm the connection | One of my PATs has `LastUsedAt` set. |

Rules:

- **Writers** are users who can write in at least one readable project (5.1, 5.3). A user who is Viewer in every project they can read sees no write items (Create a ticket, Move work forward, Join the conversation; commenting needs write access, 5.3). Follow a ticket and the optional agent items stay visible to everyone. Because any active user can create a project (D-18), Create a ticket may also link to the "Your first project" walkthrough.
- Owner items appear only when `ownsProjects` is true; Admin items only for Admins.
- Items are computed on the server and returned as ids with `done` and `optional`, in the order above (D-135). Work in a project the user can no longer read, or in a deleted project, does not count; archived owned projects do not count as owned. Watching a ticket automatically (as its reporter, for example) counts as following it.
- Optional items do not hold back completion. When every other visible item is done, the card shows a completed state, records `checklist` `Completed` and stops appearing on My work after the visit (or after Hide).
- The card can be dismissed, which records `checklist` `Dismissed`; Help → Getting started (with the progress, for example "3 of 8") forgets the stored state with `DELETE /me/onboarding/guides/checklist`, opens My work and focuses the card, so it shows again until it is dismissed or completed again.
- The card refreshes when My work is shown and when the window regains focus, so actions done in another tab, over REST or over MCP tick items off. A skeleton shows while the state loads. Each open item links to where its action is done: the create-ticket dialog, the backlog of a project the user can write to, the settings, test cases or regressions of a project they own, Boards, Admin → Users or Agent prompts, or Profile → Access tokens; the first open item shows what to do next ("Press C", "Open a ticket").
- A user without write items sees a note that steps that create, move or comment are hidden because they cannot change any project yet. While the "Your first project" walkthrough is registered, the card's footer offers it.
- The card shows by itself, so it is listed in `AUTO_SHOWN_GUIDES` (14.1).
- Leak guard: no item reveals anything about a project the user cannot read; the queries are covered by a copy of `ReadableProjectsLeakGuardTests` and by a test for a user who is Viewer everywhere.

### 14.4 Tours and the anchor rule

A **tour** is a short sequence of steps on one view, each step a popover pointing at a part of the page under a spotlight. The engine is home-grown on Angular CDK Overlay and A11y (D-131):

- The spotlight is an SVG-mask backdrop in a CDK overlay, re-measured on resize and scroll. The popover is positioned next to its anchor, traps focus, has `role="dialog"` labelled by its title, and announces "Step n of m". `←` and `→` move between steps, `Esc` ends the tour, and focus returns to where the tour was started. Global shortcuts are suppressed while a step is open. Both themes and `prefers-reduced-motion` are supported.
- Tours are keyed by **view id** (6.13), never by variant. Definitions are plain data (no Angular imports) under `core/onboarding/tours/`, so e2e specs can import them, and they reference anchors by string id only, so core never imports a feature.
- A step may declare `requires: write | owner | admin`; steps the user may not perform are left out, so Viewers get a read-only tour.
- A step whose anchor is missing is skipped (with a warning in development builds). If fewer than half the anchors of a tour resolve, the tour does not start.
- A tour closes when the peek panel or another overlay opens.
- Finishing a tour records `Completed`, ending it early records `Dismissed`; both can be replayed from the Help menu or the palette.
- Each tour has the guide id `tour.<viewId>` and a version; raising the version shows it again to users who completed or dismissed an older one. A tour that did not start (too few anchors) or gave way to the peek, another overlay or a navigation records nothing. Access comes from the user's effective role in the open project (Owner and Member write unless the project is archived; Admins are Owner everywhere) and the instance Admin role. Views without an open project report their own access: a board from its linked projects, a ticket page from the ticket (D-138).
- **Starting a tour.** "Tour of this page" in the Help menu starts the tour of the current view and is disabled, with the hint "No tour here", on views without one. The palette's Help group has one command per tour (`help.tour.<viewId>`, "Backlog tour"). On its own view it starts the tour; a tour whose view needs only a project (the backlog) can also be started from anywhere: it opens that view in the project in context, else in the most recently updated project the user can write to, else the most recently updated readable one, and starts once the view has loaded. Focus returns to the Help menu trigger (or to what the palette gave focus back to).

**Anchor rule** (D-131, extends ADR 0008): a tour anchor is a stable id on an element, set with the `tkTourAnchor` directive (for example `tkTourAnchor="backlog.quick-create"`), which renders `data-tour` and registers the element. Anchors are separate from `data-testid`. **Every variant of a view exposes the same anchor ids.** Sections added to the ticket view through `provideTicketDetailSection` expose their own anchors. `e2e/tests/onboarding/tour-anchors.spec.ts` opens every tour's view with seeded data and fails as soon as an anchor disappears; a Vitest test asserts that every tour's view id is registered in the view registry. A tour for one audience declares it on its catalogue entry (`requires: owner | admin`); others get neither "Tour of this page" nor its palette command (D-139).

Per-view tours:

**"Your first project" walkthrough** (`tour.first-project`, TKT-80). Unlike the per-view tours, it spans several views, and each step advances only when the user really does the action, never by clicking Next. The user creates every record, so nothing is seeded (this is not the LATER "sample projects").

0. **Start.** A user who already owns a project chooses **Use &lt;project&gt;** or **Create a practice project**; anyone else goes to step 1.
1. **Create a private project.** The create-project dialog opens with suggestions: the name "&lt;display name&gt;'s sandbox", a free key derived from it, visibility **Private** (D-32); the step explains that other people cannot see it and that to them it answers not found. Done when the project exists.
2. **Create a ticket** in its backlog through quick-create, suggested title "My first ticket". New work lands in the backlog first. Done when the ticket exists.
3. **Change its status** (optional, can be skipped): any status can move to any status, and there is no workflow to configure. Done when the status changes.
4. **Create a board** that links the project, suggested name "My first board". Done when the board exists and links the project.
5. **Place the ticket on the board** (backlog "Move to…" or the board's add-from-backlog). A ticket lives in exactly one place: its backlog or one board (6.4). Done when the ticket's location is that board.
6. **Open the project dashboard** and run the `project.dashboard` tour steps: the numbers now include the user's ticket, and every count links to search.
7. **Finish:** keep the sandbox, invite people (project settings) or archive it. Only Admins can delete a project, once it is archived, and its key stays reserved (D-10).

Rules of the walkthrough:

- Steps are action-driven (`advanceWhen`: a predicate over app state or a route match) and may cross routes. A step counts the action however it was done, for example a ticket created with `c`.
- When the user navigates away from the step's route, the walkthrough pauses without closing and shows a small **Continue the walkthrough** pill; `Esc` or Dismiss ends it.
- Restarting resumes at the first step whose condition is not met for the chosen project, so nothing is created twice.
- Nothing is created without the user confirming the dialog. Suggested names and keys never collide with existing ones (4.3, D-10): a taken name or key gets a suffix, and a validation error leaves the step open.
- Finishing records `tour.first-project` `Completed`. Because its actions are real data, they also tick the matching checklist items (14.3).
- Entry points: Help menu and palette (`help.tour.first-project`), the projects list, boards list and dashboard empty states (14.7), and the welcome dialog's Take the tour for a user who cannot write to any project yet (14.2).

How it behaves (TKT-80, D-142):

| Step | Page and anchor | Done when (read from real data) | The card's button |
| --- | --- | --- | --- |
| 0 Start | A dialog, only for a user with an explicit Owner membership of a live project | — | **Use &lt;project&gt;** (the project the walkthrough last used, else the most recently updated owned one), **Create a practice project**, Cancel |

While the user's own dialog, picker or the peek is open the card and spotlight step aside, and come back when it closes. The step re-reads its condition when it starts, after any successful write of the app, after a navigation, when the user's overlay closes and when the window regains focus; it never polls.
- Steps 6 and 7 are ordinary modal tour steps (focus trapped, shortcuts paused, `←` `→`). The card's eyebrow reads "Your first project · Step n of 7"; the five dashboard steps count as step 6.
- **Paused**: a navigation the walkthrough did not start first re-checks the step (finishing a step elsewhere, for example the board page opening after a board was created, just moves on); otherwise, off the step's page, the card goes and the pill at the bottom shows "Paused at step n of 7 · &lt;title&gt;" with **Continue the walkthrough** and × (Esc inside the pill also ends it). Help → Your first project (hint "Paused") and the palette command also continue it. A reload drops the pill; starting again resumes from data.
- **Resume**: the start checks every action step's condition in order for the chosen project, passing params on (project key, ticket key, board id), and opens the first that does not hold. The optional status step is passed over when a later step already holds; the boards list's "How boards work" also passes over it, so a user with a project and a ticket starts at Create a board.
- **Dismiss** (×, Esc, End walkthrough, the pill's ×) stores `tour.first-project` `Dismissed`; Done on step 7 stores `Completed`. Starting from any entry point works in either state.

### 14.5 Contextual hints

A **hint** is a small inline note shown at the moment of likely confusion. It is part of the page (a `shared/ui` component), not an overlay, so it never suppresses shortcuts or fights a tour. It has a dismiss button that records `hint.<id>` `Dismissed`; Restart all guides brings it back.

Rules (D-137):

- A hint shows until the user dismisses it ("Got it", or × in a picker), which records `hint.<id>` `Dismissed` at the hint's version. Raising the version in code shows it again; Restart all guides brings every hint back.
- Nothing shows until the onboarding state has loaded (14.1). No hint shows while a tour runs, or while a dialog, menu or picker with a backdrop covers the page; a hint inside a picker is covered only by overlays other than its own picker.
- At most one hint is on screen: of the hints placed on the page, the first one registered that is unseen, allowed and not covered wins. Opening a status picker on the backlog therefore swaps the backlog hint for the picker's hint until the picker closes.
- Hints are inline (`role="note"`), never focus-stealing; the dismiss button is a normal button in the tab order. In a picker, Tab from the filter moves to the hint's × (Shift+Tab goes back) and Enter or Space dismisses it, after which focus returns to the filter with the picker still open; Tab past the ×, or Escape, closes the picker. Without a visible hint, Tab closes the picker as before (D-157).
- Copy lives in `core/onboarding/guides/hints.ts` with stable ids (I-60). Hints are listed in `AUTO_SHOWN_GUIDES`, so the e2e suites mark them seen (D-134).

## 15. Achievements

Users earn private, tiered achievements for real actions, through any channel. They make the app more pleasant and nudge people towards features they haven't tried. They are not a performance metric. Epic TKT-61; decisions D-144 (privacy, HR/DPO position, no backfill) and D-145 (criterion definitions, start stamping). The domain term is **Achievement**; "Badge" is the design system's UI component.

### 15.1 Feature flag and privacy

- Everything sits behind the string-variant flag `achievements` (6.13), evaluated per user: the projector, the REST API, the MCP tools and the UI. While it is off for the caller, every achievements endpoint returns 404 `achievements.disabled` and the MCP tools are missing from `tools/list` (`AchievementsGate`, the same pattern as `AgentGate`).
- An achievement is visible only to its owner, Admins included. There is no admin or manager view of individuals, no leaderboard (not even per team), no export, no points and nothing time-based (no streaks, night-owl or weekend achievements). A user may share an individual achievement (TKT-97); others then see its name, icon and tier, never dates (D-144).
- No project or ticket id is stored with an achievement, so nothing can reveal a private project.
- Achievements are monotonic: an earned tier is never revoked, even when the counted entities are later deleted. Only the opt-out deletes them.
- On by default. A one-click opt-out deletes the user's achievement data (15.11, TKT-68). User anonymisation (I-57) deletes it too.

### 15.2 Catalogue

The catalogue is code (`AchievementCatalog`), not an admin-editable table. Each entry has a stable id (lower-case kebab case, at most 50 characters, never renamed or reused), a name, a description, a "how to earn" hint (non-secret entries only; secret entries stay masked until earned), a Tabler icon name in kebab case, ascending tier thresholds and a secret flag. A once-only achievement has the single threshold 1. Each entry has exactly one criterion (15.4); adding one is described in backend.md ("Adding an achievement").

### 15.3 Data

- `users.achievements_hidden` (bool, default false): the user opted out.
- `users.achievements_started_at` (timestamptz, null): the user's start **S**. Only activity at or after S counts.
- `user_achievements(user_id, achievement_id varchar(50), tier smallint, unlocked_at, seen_at null)`, primary key `(user_id, achievement_id, tier)`, deleted with the user. One row per earned tier; `seen_at` is set when the owner has seen the unlock (TKT-67). `shared_at` (null) is set on the tier-1 row while the owner shares the achievement (15.7, D-150).
- `achievement_projector_state(id, processed_until)`: the projector's single-row watermark (TKT-64).

### 15.4 Criteria

Counts come from data that is already recorded: `activity_entries` (every channel writes through `IActivityLog`, which stamps actor and channel) and creator columns of tables. The rules shared by every criterion (D-145):

- **After S only:** `occurred_at >= S` for activity, `created_at >= S` for table rows. There is no backfill.
- **Distinct entities per user:** an entity counts once for a user however often the action repeats (moving a ticket in and out of Done counts once). Someone else's action on the same entity doesn't matter.
- **Alive entities only:** a ticket counts while it and its project are not deleted (archived projects and boards still count); a doc while it and its project are not deleted. Exceptions are listed below.
- **Every channel:** web, REST with a PAT and MCP all count, except where a criterion is about the channel.
- **No other user's data:** a user's count reads only their own entries and rows.

| Id | Counts, for user U after S |
| --- | --- |
| `reporter` | Alive tickets U created (`tickets.created_by_id`): single, batch and regression bugs. |
| `bug-hunter` | `reporter` tickets whose type is Bug when evaluated. |
| `closer` | Distinct alive tickets U moved to Done (a `status` change by PATCH, MCP or a board move). A ticket created in Done has no status change and doesn't count. |
| `exterminator` | `closer` tickets whose type is Bug when evaluated. |
| `ready-for-review` | Distinct alive tickets U moved to Review. |
| `triage` | Distinct alive tickets U assigned to another user, at creation (`assigneeId` in the `ticket.created` entry) or later (an `assignee` change). Assigning yourself, including the delegation auto-assign, and unassigning don't count. |
| `conversationalist` | Comments U wrote on alive tickets and docs that are not deleted. |
| `connector` | Links U added that still exist (links are removed on unlink and when a linked ticket is deleted). Includes the link added when filing a regression bug. |
| `show-me` | Attachments U uploaded to alive tickets and docs that still exist. |
| `test-author` | Test cases U created that still exist (archived ones count), in projects that are not deleted. |
| `regression-runner` | Distinct session items U recorded a result for, other than resetting to Waiting for execution; projects not deleted. |
| `found-it` | Alive bugs U filed from a failed regression item (Create bug, or `createBug` when recording). |
| `full-sweep` | Regression sessions U completed (not cancelled); projects not deleted. |
| `board-builder` | Boards U created that are not deleted. |
| `spring-cleaning` | Boards U archived, even if they were deleted later. |
| `delegator` | Distinct alive tickets U delegated to an agent (web only). |
| `machine-whisperer` | Any activity U wrote over MCP. MCP calls that write no activity (watch, unwatch, mark notifications read), reads and REST with a PAT don't count. |
| `epic-finisher` | An Epic U moved to Done that, when evaluated, is alive and still Done and has at least one non-deleted **direct** child, all of them Done. A childless Epic doesn't count. The children's state is read at evaluation, so an Epic closed before its last child counts once that child is Done (D-148). |
| `shout-out` | U's first new ticket, description change, comment or comment edit that newly mentions a user other than U, on an alive ticket and, for comments, a comment that is not deleted. Mentions are found with the D-96 rules (`MentionRules`): a new text counts every mention, an edit only mentions the old text didn't have; self-mentions and mentions in code don't count. Doc-comment mentions don't count (D-96). Users who already hold it are skipped (D-148). |
| `second-thoughts` | A ticket or doc U restored that U deleted: the latest `ticket.deleted` or `doc.deleted` entry of that ticket or doc before the restore is U's, at or after S, and the restore came within the undo window (10 minutes). An Owner restoring someone else's delete, or an older delete from the trash, doesn't count; neither does restoring a doc version. Ticket delete and restore are Owner-only, so Members earn it through docs. |
| `unblocker` | A ticket U moved to Done that, when evaluated, is alive and still Done and is the source of a Blocks link to at least 3 alive tickets that are not Done. Tickets that block it, and other link types, don't count. |
| `grand-tour` | A ticket U worked on, meaning U changed its status at least once after S, whose status changes after S by anyone cover all 8 statuses, counting both the old and the new status of each change (so the status it had at S counts). Alive tickets only. |

The evaluator computes every criterion for a batch of users, each with their own S, in a fixed number of queries that does not depend on the number of users, and returns per user and achievement the current count and the tier it reaches (the progress TKT-65 shows). It never writes; the after-commit projector (TKT-64) awards tiers. It is not an `IActivityObserver`, so an evaluator failure never fails a user's write (D-144).

### 15.5 Start of counting (S)

- S is stamped the first time the flag is seen on for a user whose S is empty: by the achievements API (`AchievementsGate` sets S to now), or by the projector when it finds the user's activity (S is then the earliest entry of the current cycle window, so the first action after the flag flip is not lost).
- Turning the flag off and on again keeps S. The flag is an operational switch, not an opt-out, so activity while it was off counts once it is back on.
- Opting out sets `achievements_hidden`, clears S and deletes the user's achievements. Opting back in sets S to now: counting restarts from zero.
- A user who opted out gets no S and is skipped by the projector.

### 15.6 REST and MCP

Every endpoint and tool serves the caller's own achievements only, Admins included: none takes a user id, and none returns or changes another user's rows (TKT-65). Showing a shared achievement to others is the separate read path in 15.7. While the flag is off for the caller, and after they opted out, every endpoint returns 404 `achievements.disabled` (the opt-out answer carries a hint to opt back in) and `list_my_achievements` fails with that code. Every call stamps S as in 15.5 (D-147).

| Method and path | Purpose |
| --- | --- |
| `GET /api/v1/me/achievements` | `{ startedAt, items }`: S, and the whole catalogue in catalogue order. An item is `{ id, name, description, howToEarn, icon, secret, masked, tier, shared, tiers: [{ tier, threshold, unlockedAt, seenAt }], progress: { count, nextTier, nextThreshold } }`. `tier` is the highest tier earned (0 for none); `shared` is true while the caller shares it (15.7), false for unearned and masked entries; `unlockedAt` and `seenAt` are null while a tier is not earned or not seen. `progress.count` is computed live by the evaluator for the caller from S; `nextTier` is the tier after the highest earned one and `nextThreshold` its threshold, both null once the top tier is earned (the count can reach it shortly before the projector awards it). `howToEarn` is null for secret entries. A secret entry not earned yet is masked: `masked: true`, `secret: true`, `tier: 0`, `tiers: []` and `id`, `name`, `description`, `howToEarn`, `icon` and `progress` null. |
| `GET /api/v1/me/achievements/unseen` | `{ count, items: [{ id, name, tier, icon }] }`: the caller's earned tiers with no `seenAt`, oldest unlock first, one item per tier. The unlock toast polls it with the notification poll; it evaluates no criteria and answers in under 50 ms (p95), like the unread count (6.16). |
| `POST /api/v1/me/achievements/seen` | `{ ids: [...] }` (1 to 100 achievement ids): sets `seenAt` on every earned, unseen tier of those achievements; a tier already seen keeps its time, unknown or unearned ids are ignored. Returns the remaining unseen tiers in the `GET /unseen` shape. Needs write-scoped credentials (a ReadOnly PAT gets 403 `pat.readOnlyScope`); `validation` (400) for no ids or more than 100. |

`GET` accepts any credential (cookie or PAT, read-only included). The read-only MCP tool `list_my_achievements` (no inputs) returns the `GET /api/v1/me/achievements` shape and is listed in `tools/list` only while the flag is on for the token's user (`[FeatureGate(typeof(AchievementsGate))]`). Marking seen has no tool: it is personal UI state.

### 15.7 Sharing

A user may share individual earned achievements; everything else stays visible only to them (D-144). A shared achievement is visible to **every signed-in user**, with no shared project needed, and Admins see no more than anyone else. Nothing is shared until the user shares it. Decision D-150 (TKT-97).

- **Storage:** `user_achievements.shared_at` on the achievement's tier-1 row (15.3). The projector always inserts every tier up to the one reached, so the tier-1 row exists whenever any tier is earned. A share covers the achievement, not a tier: others see the highest tier, including tiers earned after sharing.
- **Opt-out** deletes the user's `user_achievements` rows (TKT-68), and the shares with them; nothing else needs deleting.

| Method and path | Purpose |
| --- | --- |
| `PUT /api/v1/me/achievements/{id}/share` | Shares the caller's earned achievement `id`. Idempotent: sharing again keeps the first `shared_at`. Returns the item in the `GET /api/v1/me/achievements` item shape, with `shared: true`. 404 `achievements.notEarned` when the caller has not earned it, unknown ids included (a secret id reveals nothing). Needs write-scoped credentials (403 `pat.readOnlyScope`). Like every `/me/achievements` call: 404 `achievements.disabled` while the flag is off for the caller or after an opt-out, and it stamps S. |
| `DELETE /api/v1/me/achievements/{id}/share` | Stops sharing it. Idempotent; same response, errors and credentials as `PUT`, with `shared: false`. |
| `GET /api/v1/users/{id}/achievements` | `{ items: [{ id, name, icon, tier }] }`: the user's shared achievements in catalogue order, `tier` the highest earned. Never dates, counts, progress or anything about projects or tickets; unshared, unearned and secret-but-unshared achievements are never returned. Any signed-in user and any credential (read-only PAT included); `200` with empty `items` while the user shares nothing. 404 `achievements.disabled` while the flag is off for the viewer. 404 `user.notFound` when the user is unknown, deactivated, opted out or has the flag off, so the answer never tells which. It does not stamp the viewer's S, and a viewer who opted out may still read others' shares. |

MCP: `share_achievement` and `unshare_achievement` (input `id`) call the same handler as `PUT` and `DELETE` and return the same item; they are idempotent, need a read-write token and are listed only while the flag is on for the token's user. Reading another user's shares has no tool: the web app's user card (TKT-98) is its only consumer. The response carries no user data at all, so the card's name-only rule (no email) holds.

### 15.8 Projector

Tiers are awarded after commit by the `AchievementProjector` background service, never inside a user's write (D-144, D-149), so a failing criterion cannot fail or slow a save.

- **Cycle** (every `AchievementProjector:Interval`, default 15 s): under an advisory lock, in one transaction, it reads the users with activity since the watermark minus a 2-minute overlap (`occurred_at` is stamped before commit). It keeps those who are active, have not opted out and have the flag on (evaluated for the whole batch at once), stamps S where it is empty (15.5), evaluates only the criteria their actions trigger and that they do not hold at top tier, inserts every newly reached tier and advances the watermark. Without a watermark the first cycle starts 2 minutes back: there is no backfill.
- **Idempotent:** tiers are inserted with `ON CONFLICT DO NOTHING` and counts are recomputed from source data, so re-running a cycle or the sweep adds nothing. Every unlock is unseen (`seen_at` empty).
- **Failure:** a failing cycle rolls back, including the watermark, is logged and is retried on the next interval, so nothing is lost.
- **Nightly sweep** (`AchievementProjector:SweepAtUtc`, default 03:00 UTC): the same evaluation over the whole catalogue for every active, started, non-hidden user with the flag on, in batches of 500. It never stamps S, so it covers only activity after each user's start.
- Deactivated users, users who opted out and users with the flag off are skipped and get no S.

### 15.11 Opt-out

Achievements are on by default; each user can turn them off, and doing so deletes their data (D-144, TKT-68, D-153).

- **API:** `PATCH /api/v1/me` takes `achievementsHidden` (boolean, optional, next to `displayName` and the avatar fields), through `UpdateMyProfile`, web session only like the rest of `PATCH /me` (a ReadOnly PAT gets 403 `pat.readOnlyScope`, a ReadWrite PAT 403 `auth.cookieSessionRequired`). `GET /me`, `PATCH /me` and the login response carry `achievementsHidden`. There is no MCP tool: the opt-out is a personal setting, like the rest of the profile.
- **Opting out** (`true`), in one transaction: sets `achievements_hidden`, clears S and deletes every `user_achievements` row of the user, shares included, so others stop seeing them at once. It holds the projector's advisory lock, so a running cycle cannot award a tier after the delete. The projector, the sweep and the gate skip the user from then on, and every `/me/achievements` endpoint answers 404 `achievements.disabled`.
- **Opting in** (`false`): clears `achievements_hidden` and sets S to now. Counting restarts from zero; nothing from before the opt-in counts, earlier activity included (no backfill).
- Both are idempotent: opting out again deletes nothing more, opting in again keeps S.
- **Flag off:** while the `achievements` flag is off for the caller, a request with `achievementsHidden` is rejected with 404 `achievements.disabled` and nothing in it is applied, other fields included. Requests without it are unaffected.
- The change is not written to the activity log: who opted out is not visible to anyone else (D-144).
- **Web:** Profile → General has an Achievements card while the flag is on (`docs/design/mockups/achievements.html` §6): an "Earn achievements" switch, on by default, with the copy that they are private unless shared. Turning it off opens an inline confirm, "Turn off and delete your achievements?", with "Turn off and delete" and "Keep them"; turning it on needs no confirm. The save is optimistic: the Achievements tab and every other achievements element disappear (or return) at once through `AchievementsAccess`, and roll back with an error toast if the save fails.

### 15.12 User card and sharing in the web app

The look is `docs/design/mockups/achievements.html` (tab, detail and "A teammate's shared achievements"), layout-and-screens §2 "User card" and the design system's "Achievement medal" (TKT-98, D-155).

- **Share on the tab:** every earned tile has a Share control ("Share", or "Shared" that reads "Unshare" on hover), and the detail popover of an earned medal a Share/Unshare button with a line on who sees it. A shared medal carries the shared marker and its accessible name ends in ", shared" (owner's views only). The change is optimistic: the medal switches at once, the server's item replaces it, a failure puts it back with a danger toast (Retry), and success shows "Reporter is shared" / "Reporter is no longer shared" with Undo. `S` shares or unshares the focused tile (no other `S` shortcut is registered on the profile pages).
